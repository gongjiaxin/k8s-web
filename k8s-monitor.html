🕰️ 全链路流程图:从"用户访问"到"报警送达"再回到用户(事件流视角)

上面那张是静态结构(谁连谁);这张换成时间线 —— 以一次业务故障当剧本,四幕走完监控闭环。对应用户口中的四个词:用户访问 = 第 0 幕,采集 = 第 1 幕,监控 = 第 2 幕,报警 = 第 3 幕(第 4 幕是闭环):

👤 第 0 幕 · 用户访问业务 —— 一切的起点,也是一切监控的意义

  • 用户/浏览器 → Ingress/NodePort → 业务 Pod(Spring/Go/…)
  • 正常时无人知晓;出事时用户最先感知(变慢/5xx/白屏)
  • 用户的体验不会自动告诉运维 —— 必须让数据说话,于是有了下面三幕
▼业务 Pod 与节点指标一直在产生,等监控来取

📡 第 1 幕 · 采集(全自动,无人工参与,15~30s 一轮)

  • 四路指标源:node-exporter(节点 CPU/内存/磁盘) · kube-state-metrics(对象状态/重启次数) · kubelet+cAdvisor(容器运行时) · 业务自暴露 /metrics
  • Prometheus 主动 Pull 各 Target 的 /metrics → TSDB 落本地盘(保留 15~30d)
  • Target 挂了指标 up==0 —— 数据断流本身就是一条告警
▼数据已入库,两条使用路径并行:左边"人主动看"(监控),右边"机器自动喊"(报警)
▲人主动查(Grafana → Prometheus)

📊 第 2 幕 · 监控 —— 人主动看(巡检/容量/趋势)

  • 运维浏览器 → Grafana:3000 → 选 Dashboard(315 集群 / 8588 自身 / 1860 节点)
  • Grafana 拼 PromQL → Prometheus /api/v1/query 取数 → 出图
  • 适合白天主动巡检;但人不可能 24h 盯屏 —— 半夜的事交给右边
▼机器自动评估(Prometheus → AlertManager)

🚨 第 3 幕 · 报警 —— 机器自动喊(7×24 不眨眼)

  • Prometheus 周期评估规则(如 container_memory_working_set_bytes > limit×90% 持续 5m):pending → firing
  • Push /api/v2/alerts → AlertManager:去重/分组/静默/路由
  • webhook/smtp → 钉钉/企业微信/邮件 → 值班手机响
  • ❗这条线断了的下场:线上 InfluxDB OOM 156 天/4256 次重启无人知(k8s-oom 档案)
▼(报警路径)值班的人被叫醒,进入处置

🔧 第 4 幕 · 处置闭环 —— 回到第 0 幕的用户

  • 收到告警 → kubectl describe pod(看 OOMKilled/重启计数,数据来自 kube-state-metrics)→ 定位修复(调 limit/扩容/重启)
  • 指标回落 → Prometheus 推 resolved → AlertManager 再发一条"已恢复" —— 告警有始有终
  • 用户访问恢复正常:四幕闭环完成;复盘沉淀(改阈值/加规则),监控越用越准

图:监控全链路事件流 —— 第 1 幕采集供数据,第 2 幕监控给人看,第 3 幕报警替人守,第 4 幕处置回到用户;蓝框 = 报警主链(Prometheus 评估 + AlertManager 分发)

💡 一句话记住:Prometheus 是心脏(数据进、规则算、查询出),AlertManager 是嘴(替它喊话),Grafana 是脸(替它露面)—— 心脏不跳,嘴和脸都没意义,所以先装心脏。

02先装哪一个?结论与理由

结论:Prometheus → AlertManager → Grafana

顺序组件角色为什么排这个位置装完验证
① 第 1 个 Prometheus 核心引擎 另两个都依赖它;单独装即完整可用(采集+存储+自带查询页) Web UI 9090 → Status/Targets 全 UP;能查到 up 等指标
② 第 2 个 AlertManager 告警下游 被动收 Prometheus 推送;装好后在 Prometheus 配 alertmanagers 地址 造一条必触发规则(如 up==0),AlertManager UI(9093)能看到 alert
③ 第 3 个 Grafana 展示层 无任何组件依赖它;只需加数据源,随时可装 Data Source 测试连通;导入 Dashboard 315 能出图

为什么 AlertManager 排第二,而不是第一?

有个看似反过来的理由:Prometheus 配置里要写 AlertManager 的地址,似乎该先把 AlertManager 建好?注意区分两件事:

  • 依赖的本质是"谁离了谁不能工作":AlertManager 单独存在毫无意义(没告警可收),Grafana 单独存在毫无意义(没数据可画),而 Prometheus 单独存在完全可用。
  • 没装 AlertManager 时,Prometheus 照常采集存储,只是告警发不出去(日志报 connection refused)—— 不影响核心功能。
💡 手动 YAML 部署的小技巧:可以先创建 AlertManager 的 Service(拿到稳定的 ClusterDNS,如 alertmanager.monitoring.svc:9093),再装 Prometheus 时一次性写好 alerting 配置 —— 避免后改配置重启。这是"Service 先行",不是"组件先行"。

03依赖矩阵与易混淆点 —— 数据流 ≠ 依赖方向

依赖矩阵:谁离了谁不能工作

组件依赖谁被谁依赖单独存在是否有意义结论
Prometheus 无(零依赖,只依赖被抓对象活着) AlertManager(收它的推送)、Grafana(查它的数据) ✅ 完整可用:采集+存储+自带 9090 查询页 第 1 个装
AlertManager Prometheus(功能上:没它推送就永远无事可做) 无人依赖 ❌ 空转:一个告警都不会有 第 2 个装
Grafana Prometheus(数据上:没数据源的看板是空壳) 无人依赖 ❌ 空壳:连了 MySQL/Loki 才另当别论 第 3 个装

数据流向 vs 依赖方向(最容易搞混的一张对比)

数据流向(运行时,数据怎么走)              依赖方向(部署时,谁必须先在)
─────────────────────────────            ─────────────────────────────
Target ←─ pull ── Prometheus             Prometheus(根,0 依赖)
Prometheus ── push ──► AlertManager              ├─► AlertManager(等它来推)
Prometheus ←─ query ── Grafana                   └─► Grafana(来查数据)
AlertManager ── webhook ──► 钉钉/邮件
                                          部署序 = 从根往下:① P → ② A → ③ G
推 push / 拉 pull 的主动方都是箭头尾         (数据流的主动方 ≠ 先装的一方!)

三个常见误区

误区一:"Prometheus 配置里写了 AlertManager 地址,所以 Prometheus 依赖它" —— 错,那只是配置引用;没它 Prometheus 照常采集存储,只是告警发不出去。
误区二:"Grafana 是看监控的,得先有 Grafana 才能确认 Prometheus 装好了" —— 错,Prometheus 自带 9090 Graph 页,先装完先用它自验,Grafana 只负责好看。
误区三:"AlertManager 会主动去 Prometheus 拉告警" —— 错,方向正好相反:Prometheus 推、AlertManager 收;所以网络策略只需放行 Prometheus → 9093 这一条。
💡 装前自检三问:① 抓谁?(先部署 node-exporter/kube-state-metrics 这些采集端)② 数据存哪?(Prometheus 的 PVC 与保留天数)③ 告警发给谁?(AlertManager 的路由与接收器)—— 三问答完,安装顺序自然就是 ① ② ③。

local-path 特性(读表要点)对安装的影响

1. 加仓库 + 裁剪 values(不裸装)

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm search repo prometheus-community/prometheus

这个 chart 是"一父多子"结构:server(Prometheus 本体)、alertmanager、nodeExporter、pushgateway、kube-state-metrics,各自一个开关。按第 01 节的顺序,先只装 Prometheus 本体 + 采集端:

mkdir -p ~/monitor && cat > ~/monitor/prom-values.yaml <<'EOF'
## ============ Prometheus 本体 ============
server:
  enabled: true
  retention: "7d"                # 测试环境 7 天足够,生产 15d~30d
  persistentVolume:
    enabled: true
    size: 10Gi                   # local-path 不能扩容,一次给够
    # storageClass 不写 = 用默认 local-path
  resources:
    requests: {cpu: 200m, memory: 768Mi}
    limits:   {cpu: "1",  memory: 2Gi}
  service:
    type: ClusterIP              # 先 ClusterIP 验证,要域名见本章第 5 步 ingress 段

## ============ 周边组件按需裁剪 ============
alertmanager:
  enabled: false                 # ← 第二步再开(第 05 章)
nodeExporter:
  enabled: true                  # 节点指标,保留
pushgateway:
  enabled: false                 # 临时任务推送用,暂时不需要
EOF
💡 enabled: false 的组件 Helm 根本不会创建,后面想加回来改 values 再 helm upgrade 即可 —— 这正是按"①②③"顺序分步装三件套的底气。

方案链路特点入口

⭐ 灵魂三问:不写端口 = 默认走 31588?配了 class = 另启动一个 ingress?二者区别?先把两个角色分开 —— Ingress 资源只是一张路由规则单(host/path → svc):不是进程、不监听端口,写多少条都不"启动"任何东西;真正干活的是 IngressController(nginx Pod + NodePort svc):读规则单、守入口端口。"选 class"本质是"选执行者":

灵魂三问答案
① Ingress 里不写端口,
默认就走 31588?		结论对,机制不是"默认"而是"class 决定":入口端口 = ingressClassName 对应那套 controller 的 Service 端口 —— nginx → 共享款 31588;prometheus-nginx → 专属款 30990。若连 ingressClassName 都不写,则找集群标记为 default 的 class(kubectl get ingressclass 看 DEFAULT 列;无 default 时规则无人认领)—— 建议永远显式写 class
② class 配成 prometheus-nginx,
等于另启动了一个 ingress?		半个对,拆成两步看:改 Ingress 的 class 本身零成本、零新增 —— 只是规则单换了"认领人"(从共享 controller 搬家,31588 随之 404);但新 class 要有人认领,必须先 helm 装一套新 controller(下方 ② 步命令)—— 这一步才是"另启动一个 ingress":集群多一个 nginx Deployment(1 Pod,约 0.5C/0.5G 起)+ 一个 NodePort svc。只改 class 不装 controller = 规则无人认领,30990 必然不通
③ 共享 vs 独立
到底差在哪?		见下表五维对比 —— 一句话:共享 = 全楼共用一个门卫(31588 一扇门,按 Host 分流);独立 = 每栋楼自带门卫(30990 专属门,端口即隔离)
维度A · 共享(class=nginx,31588)B · 独立 controller(class=prometheus-nginx,30990)
新增成本★零:只加一条 Ingress 规则,复用现有 controller多一套 Deployment(Pod)+ 一个 svc,吃节点资源
入口端口所有域名同挤 31588,靠 Host 分流专属 30990,端口即业务边界 —— 外层 NGINX 的 upstream 按端口指认,互不干扰
故障域controller 重启/挂 → 所有站点一起断互不影响,排查范围天然缩小
变更影响升级 controller/改全局配置 = 动所有人的门可独立升级、回滚、调参(如 Prometheus 款放宽超时,不影响 k8s-web)

  ↓

  ↓  集群内 HTTPS POST 对象 JSON(唯一调用方,就这一次)

  ↓ 校验 annotation / snippet / 规则语法
通过 → 对象落库 → controller watch 到 → 生成 nginx 配置 reload → 31588 生效
拒绝 → kubectl 当场报错,坏配置进不了集群
为什么"只有 443"原因
没有 8080 是业务 HTTP 流量的端口(那是 controller svc 80:31588 的职责);webhook 属管理面,API Server 调 webhook 强制 TLS/HTTPS,所以只听 443(targetPort 8443)
没有 NodePort唯一调用方是 API Server,集群内部网 POST 一次 ClusterIP 即达;暴露到节点/外网反而给外人乱敲"安检门"的机会
它挂了会怎样webhook 默认 failurePolicy: Fail:不可达时所有新建/更新 Ingress 全被拒,报 failed calling webhook validate.nginx.ingress.kubernetes.io(harbor 装第二套 controller 时实测踩过,见 Harbor 文档)。应急:修 svc 指向,或临时删对应 validatingwebhookconfiguration 放行
💡 回退与顺序:要回方案 A 只需把 Ingress 的 ingressClassName 改回 nginx 再 apply、外层 NGINX upstream 同步改 31588。注意 30990 在装好 controller 前必然不通,顺序是加仓库 → 装 controller → 切 class → 验端口。

7.11 PromQL 常用查询速查手册(31 条 · 分 8 组)

💡 用法:全部可在 Prometheus UI(https://new-prometheus.fftaicorp.com → Graph)或 Grafana 的 Explore 页直接粘贴;时间窗 [5m] 按需改,[1h] 看趋势、[5m] 看当下。这些语句同时是自建 dashboard 和告警规则的原料 —— 看板是它的曲线形态,告警是它 + 阈值。

① 节点系统层(sys 体检 · node_*)

# CPU 使用率%(整节点)
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
# CPU 每核负载(load1/核数,>1 = 过载)
node_load1 / count by (instance) (node_cpu_seconds_total{mode="idle"})
# 内存使用率%
100 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes * 100)
# 磁盘空间使用率%(排除 tmpfs/overlay 伪文件系统)
100 - (node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"} * 100)
# 磁盘繁忙度%(有 IO 在进行的时间占比,持续 >80 = 瓶颈)
rate(node_disk_io_time_seconds_total{device!~"loop.*"}[5m]) * 100
# 磁盘读写吞吐(B/s)
rate(node_disk_read_bytes_total[5m]) + rate(node_disk_written_bytes_total[5m])
# 网卡流量(B/s,收+发,排除 lo)
rate(node_network_receive_bytes_total{device!="lo"}[5m]) + rate(node_network_transmit_bytes_total{device!="lo"}[5m])
# 开机时长(秒)
node_time_seconds() - node_boot_time_seconds

② 容器/Pod 层(container_* + kube_*)

# 各 Pod CPU(单位:核)
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))

⑧ 高频误区:up 里只见 kube-system?业务 ns 怎么"加监控"?

up ≠ 集群 Pod 列表 —— 它是"采集目标列表"。默认 ServiceMonitor 只给 K8s 基础设施组件(kubelet/cAdvisor/kube-proxy/coredns/apiserver/etcd)建了抓取,它们恰好全住 kube-system,所以 up 一片 kube-system。业务 Pod 本来就不会自动出现在 up 里;而 kube-state-metrics 与 cAdvisor 两层早已覆盖所有 ns —— 验证:count by (namespace) (kube_pod_info) 会列出全部 ns 的 Pod 数,sum by (namespace) (rate(container_cpu_usage_seconds_total{container!=""}[5m])) 是全部 ns 的容器 CPU。
# 只有要抓"业务应用自己的 /metrics"(QPS/JVM/自定义指标)才需要动手 —— 建 PodMonitor:
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: my-app
  namespace: prometheus
  labels:
    release: prometheus      # ⚠️ 关键:Operator 默认按 release label 筛,不带会被无视
spec:
  namespaceSelector:
    any: true                # 抓所有 ns 的目标 Pod(或 matchNames: [某ns])
  selector:
    matchLabels:
      app: my-app            # 选中带该 label 的 Pod
  podMetricsEndpoints:
    - port: metrics          # Pod spec 里定义的端口名
      interval: 30s
# kubectl apply 后,Targets/up 里多出 podmonitor/... 一行 —— 这才是"添加监控"的正确姿势
💡 三条进阶技巧:① 改窗:[5m] 看当下、[1h] 看小时趋势,rate/increase 都可换;② 改维:sum by (...) 括号里换 label 就换口径(按 node/namespace/pod 任意切);③ 这些语句 = 告警规则本体 —— 后续配 receiver 时,规则就是"某条表达式 + for 持续时长 + 阈值",chart 自带的几百条规则(Grafana → Alerting → Alert rules 可查)全是这个套路。
