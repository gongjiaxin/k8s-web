01一图看懂:三者关系与依赖 ⭐

装之前先搞清楚三件事:谁连谁、数据往哪流、谁离了谁不能工作。下面这张图就是三件套的全景 —— ①②③ 圈号即推荐安装顺序,箭头即数据流向:

📦 被监控对象 —— 一切暴露 /metrics 的端点(数据源头,不属于三件套)

  • node-exporter —— 节点 CPU/内存/磁盘(DaemonSet,每节点一个)
  • kube-state-metrics —— K8s 对象状态(Deployment 副本/Pod 重启次数/Pod 非 Running)
  • kubelet + cAdvisor —— 容器运行时指标(每个节点内置)
  • 业务应用 —— 自暴露 /metrics(Spring Actuator / client_golang 等)
▼Pull 拉取 —— Prometheus 主动按 15~30s 周期来抓(方向:Prometheus → Target)

⭐ ① Prometheus —— 核心引擎:采集 + 时序存储 + 告警规则评估(必须第一个装)

  • 采集调度 —— 按配置的 scrape_targets 周期抓取,Target 挂了指标 up==0
  • TSDB 时序库 —— 指标落本地盘(K8S 里需 PVC 持久化),保存 15d~30d
  • PromQL —— 查询语言,下游 Grafana 取数、告警规则计算全靠它
  • 告警规则评估 —— 周期执行规则(如 up==0 持续 1m),触发后主动推送给 AlertManager
  • ✅ 单独即可工作:自带简陋 Web UI(9090),能查能画 —— 这是它排第一的底气
▼▼两路下游:左边推告警,右边被查数据 —— 都离不开 Prometheus 先就绪
▼push 推送告警(firing / resolved,方向:Prometheus → AlertManager)

② AlertManager —— 告警的"下游处理厂"(第二个装)

  • 被动接收 Prometheus 推来的告警,自己不发现任何问题
  • 去重 / 分组(group) / 静默(silence) / 路由(route)
  • 按 severity/team 路由到不同渠道,抑制告警风暴
▼webhook / smtp 分发

📣 通知渠道 → 值班的人

  • 钉钉 / 企业微信 / 飞书 / 邮件 / Slack
  • OOM 那次崩 156 天无人知晓,缺的就是这一环
▲query 查询取数(方向:Grafana → Prometheus)

③ Grafana —— 纯展示层(最后装,随时可装)

  • 把 Prometheus 配置为数据源,用 PromQL 画图
  • 社区 Dashboard:315(集群) 8588(Prometheus) 1860(节点)
  • ✅ 没有任何组件依赖它 —— 放最后最安全
▼浏览器访问 3000

👤 运维 / 开发看板

  • 日常巡检、容量趋势、周报截图
  • 也可再接多个数据源(MySQL/Loki/ES)

02先装哪一个?结论与理由

结论:Prometheus → AlertManager → Grafana

顺序组件角色为什么排这个位置装完验证
① 第 1 个 Prometheus 核心引擎 另两个都依赖它;单独装即完整可用(采集+存储+自带查询页) Web UI 9090 → Status/Targets 全 UP;能查到 up 等指标
② 第 2 个 AlertManager 告警下游 被动收 Prometheus 推送;装好后在 Prometheus 配 alertmanagers 地址 造一条必触发规则(如 up==0),AlertManager UI(9093)能看到 alert
③ 第 3 个 Grafana 展示层 无任何组件依赖它;只需加数据源,随时可装 Data Source 测试连通;导入 Dashboard 315 能出图

为什么 AlertManager 排第二,而不是第一?

有个看似反过来的理由:Prometheus 配置里要写 AlertManager 的地址,似乎该先把 AlertManager 建好?注意区分两件事:

  • 依赖的本质是"谁离了谁不能工作":AlertManager 单独存在毫无意义(没告警可收),Grafana 单独存在毫无意义(没数据可画),而 Prometheus 单独存在完全可用。
  • 没装 AlertManager 时,Prometheus 照常采集存储,只是告警发不出去(日志报 connection refused)—— 不影响核心功能。
💡 手动 YAML 部署的小技巧:可以先创建 AlertManager 的 Service(拿到稳定的 ClusterDNS,如 alertmanager.monitoring.svc:9093),再装 Prometheus 时一次性写好 alerting 配置 —— 避免后改配置重启。这是"Service 先行",不是"组件先行"。

03依赖矩阵与易混淆点 —— 数据流 ≠ 依赖方向

依赖矩阵:谁离了谁不能工作

组件依赖谁被谁依赖单独存在是否有意义结论
Prometheus 无(零依赖,只依赖被抓对象活着) AlertManager(收它的推送)、Grafana(查它的数据) ✅ 完整可用:采集+存储+自带 9090 查询页 第 1 个装
AlertManager Prometheus(功能上:没它推送就永远无事可做) 无人依赖 ❌ 空转:一个告警都不会有 第 2 个装
Grafana Prometheus(数据上:没数据源的看板是空壳) 无人依赖 ❌ 空壳:连了 MySQL/Loki 才另当别论 第 3 个装

数据流向 vs 依赖方向(最容易搞混的一张对比)

数据流向(运行时,数据怎么走)              依赖方向(部署时,谁必须先在)
─────────────────────────────            ─────────────────────────────
Target ←─ pull ── Prometheus             Prometheus(根,0 依赖)
Prometheus ── push ──► AlertManager              ├─► AlertManager(等它来推)
Prometheus ←─ query ── Grafana                   └─► Grafana(来查数据)
AlertManager ── webhook ──► 钉钉/邮件
                                          部署序 = 从根往下:① P → ② A → ③ G
推 push / 拉 pull 的主动方都是箭头尾         (数据流的主动方 ≠ 先装的一方!)

三个常见误区

误区一:"Prometheus 配置里写了 AlertManager 地址,所以 Prometheus 依赖它" —— 错,那只是配置引用;没它 Prometheus 照常采集存储,只是告警发不出去。
误区二:"Grafana 是看监控的,得先有 Grafana 才能确认 Prometheus 装好了" —— 错,Prometheus 自带 9090 Graph 页,先装完先用它自验,Grafana 只负责好看。
误区三:"AlertManager 会主动去 Prometheus 拉告警" —— 错,方向正好相反:Prometheus 推、AlertManager 收;所以网络策略只需放行 Prometheus → 9093 这一条。
💡 装前自检三问:① 抓谁?(先部署 node-exporter/kube-state-metrics 这些采集端)② 数据存哪?(Prometheus 的 PVC 与保留天数)③ 告警发给谁?(AlertManager 的路由与接收器)—— 三问答完,安装顺序自然就是 ① ② ③。

04Prometheus 部署实战 —— Helm 一把梭(装→验→开放)

实战环境:测试集群 qingfeng 单节点(v1.35.9 · containerd),安装时间 2026-10-30 16:58,命令与输出均为真实记录,复制即可用。路线:用 Helm 单装 prometheus-community/prometheus(想三件套一键装齐见第 07 章)。

0. 动手前 30 秒检查(两条命令避大坑)

# ① 集群里是否已有三件套?(防与 Rancher monitoring 撞车 —— 有输出就要考虑复用而非重装)
kubectl get pods -A | grep -iE "prometheus|alertmanager|grafana|node-exporter"
# → 无任何输出 = 环境干净,可全新安装 ✅

# ② 默认存储类是谁?(决定 Prometheus 数据落在哪、能不能扩容)
kubectl get storageclass
NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  7d2h
local-path 特性(读表要点)对安装的影响
本地路径存储(数据落节点磁盘)单节点无风险;以后多节点,Pod 会被"钉"在数据所在节点
ALLOWVOLUMEEXPANSION: falsePVC 不能在线扩容 → 第一次就把 size 给够(本章给 10Gi)
WaitForFirstConsumerPVC 等 Pod 起来才建 PV,get pvc 起初 Pending 是正常的,别慌

1. 加仓库 + 裁剪 values(不裸装)

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm search repo prometheus-community/prometheus

这个 chart 是"一父多子"结构:server(Prometheus 本体)、alertmanager、nodeExporter、pushgateway、kube-state-metrics,各自一个开关。按第 01 节的顺序,先只装 Prometheus 本体 + 采集端:

mkdir -p ~/monitor && cat > ~/monitor/prom-values.yaml <<'EOF'
## ============ Prometheus 本体 ============
server:
  enabled: true
  retention: "7d"                # 测试环境 7 天足够,生产 15d~30d
  persistentVolume:
    enabled: true
    size: 10Gi                   # local-path 不能扩容,一次给够
    # storageClass 不写 = 用默认 local-path
  resources:
    requests: {cpu: 200m, memory: 768Mi}
    limits:   {cpu: "1",  memory: 2Gi}
  service:
    type: ClusterIP              # 先 ClusterIP 验证,要域名见本章第 5 步 ingress 段

## ============ 周边组件按需裁剪 ============
alertmanager:
  enabled: false                 # ← 第二步再开(第 05 章)
nodeExporter:
  enabled: true                  # 节点指标,保留
pushgateway:
  enabled: false                 # 临时任务推送用,暂时不需要
EOF
💡 enabled: false 的组件 Helm 根本不会创建,后面想加回来改 values 再 helm upgrade 即可 —— 这正是按"①②③"顺序分步装三件套的底气。

4. 验收三关(9090 页面,命令行版同列)

先用 port-forward 把页面拉到本地(仅验证用,长期访问见第 6 步):

# 方式一:chart NOTES 推荐的(转发 Pod)
export POD_NAME=$(kubectl get pods -n monitoring -l "app.kubernetes.io/name=prometheus,app.kubernetes.io/instance=prometheus" -o jsonpath="{.items[0].metadata.name}")
kubectl port-forward $POD_NAME -n monitoring 9090
# Forwarding from 127.0.0.1:9090 -> 9090     ← 真实输出

# 方式二:转发 Service(更短,效果一样)
kubectl port-forward svc/prometheus-server -n monitoring 9090:80
💡 "卡着了?"—— 没卡!port-forward 是前台进程,这两行 Forwarding 就是"隧道已建立"的成功提示,只要它不退出转发就活着,Ctrl+C 才断开。保持窗口不动,另开窗口/浏览器去访问。

在服务器的另一个窗口先用命令行过三关(不开浏览器也能验收):

# 关① 活性
curl -s http://localhost:9090/-/healthy
# 期望: Prometheus is Healthy.

# 关② Targets 健康(命令行版"看绿点")
curl -s http://localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"' | sort | uniq -c
# 期望: 若干 "health":"up"

# 关③ up 指标查询(命令行版 Graph 查询)
curl -s 'http://localhost:9090/api/v1/query?query=up' | head -c 600
# 期望: "value":[时间戳,"1"] 的若干条
#页面操作(浏览器版)合格标准
①Status → Targets各 job 的 target 全 UP(绿点),尤其 kubernetes-nodes / kubernetes-pods
②Graph 查 up所有返回值 = 1
③查 container_cpu_usage_seconds_total有数据行(cAdvisor 抓通了)
⚠️ Windows 浏览器直接开 localhost:9090 不通!port-forward 绑定的是服务器的 127.0.0.1。要在 Windows 看界面,再开一条 SSH 隧道:ssh -L 9090:127.0.0.1:9090 用户@节点IP,然后 Windows 浏览器开 http://localhost:9090。链路:Windows 浏览器 →(SSH)→ 服务器 localhost:9090 →(port-forward)→ Pod:9090。

5. 全开放:Ingress + 域名(长期姿势,复用站内 ingress 那套)

port-forward 一断就失效,还占终端。"全开放"= 照 站内 Ingress 文档同款链路加一条子域名规则,测试集群入口 31588 是现成的:

浏览器 http://prometheus.ergesanbaishou.com:31588/
   │ hosts 解析到节点 IP
   ▼
ingress-nginx-controller (NodePort 31588 ← ingress.yaml 里已固定的入口)
   │ 按 Host: prometheus.ergesanbaishou.com 匹配新 Ingress
   ▼
svc prometheus-server (monitoring ns, port 80)
   ▼
Pod :9090   ← 和 port-forward 看到的是同一个页面

不用手写 YAML,values 的 server.ingress 段打开即可(Helm 统一管理,卸载不残留):

# ~/monitor/prom-values.yaml 的 server: 段里追加(与 retention 等字段平级):
  ingress:
    enabled: true
    className: nginx                       # 对应 ingress-nginx
    annotations:
      nginx.ingress.kubernetes.io/ssl-redirect: "false"   # 先 HTTP,同 k8s-web 站
    hosts:
      - prometheus.ergesanbaishou.com      # ★ 新子域名
    path: /
    pathType: Prefix

# 生效
helm upgrade prometheus prometheus-community/prometheus -n monitoring -f ~/monitor/prom-values.yaml

# 确认 Ingress 已生成
kubectl get ingress -n monitoring
# NAME        CLASS   HOSTS                             ADDRESS   PORTS   AGE
# prometheus  nginx   prometheus.ergesanbaishou.com     节点IP     80      ...   (示意)

# 先在服务器上验证(不等 DNS,Host 头模拟 —— 和验证 k8s-web 的手法一模一样)
curl -s -H "Host: prometheus.ergesanbaishou.com" http://127.0.0.1:31588/-/healthy
# 期望: Prometheus is Healthy.   ← 通了 = Ingress→Service→Pod 全链路 OK

最后在 Windows 用管理员编辑 C:\Windows\System32\drivers\etc\hosts 加一行(IP 换成实际节点 IP),浏览器访问 http://prometheus.ergesanbaishou.com:31588/:

<节点IP>    prometheus.ergesanbaishou.com
⚠️ 必须带 31588 端口!controller 是 NodePort 型入口,不监听 80,直接开 http://prometheus.ergesanbaishou.com/ 是不通的。要"无端口"体验需外层 NGINX 反代 —— 配置已备好:k8s/prometheus-nginx.conf(80 版可直接用 + 443 升级注释段),放到外层 NGINX 机器的 /etc/nginx/conf.d/(必须 .conf 后缀),nginx -t && nginx -s reload 生效;hosts 解析改指外层 NGINX 机器 IP。完整说明见 证书文档。
💡 同款套路直接复用:后面 AlertManager 加 alertmanager.ergesanbaishou.com、Grafana 加 grafana.ergesanbaishou.com —— 三个域名都从 31588 进,Ingress 按 Host 分流,正是第 01 节图里"三件套各自有门"的落地形态。
📄 独立 YAML 版(与 chart ingress 二选一):仓库里备了 k8s/prometheus-ingress.yaml(链路注释 + basic auth 注释段齐全)。要用它就先把 values 里 server.ingress.enabled 改回 false 再 upgrade,然后 kubectl apply -f k8s/prometheus-ingress.yaml —— 同 host 双开会规则重复、管理混乱。

5.5 入口方案对比:共享 31588 vs 独立 controller 30990 ⭐

高频疑问:Ingress 里为什么不写端口?31588 已被 k8s-web 用了怎么办?先纠正概念:Ingress 资源只有 host/path → Service 的映射,没有入口端口参数(设计使然),端口属于 controller 的 Service —— 31588 被多域名共享按 Host 分流本不算冲突。但本集群有更优雅的先例:harbor 单独装了一套 controller(入口 32588);照抄该模式给 Prometheus 配专属 controller + 独立端口 30990,端口与规则全隔离,还不丢 Ingress 层能力:

方案链路特点入口
A · 共享域名:31588 → 共享 controller → Ingress → svc:80一个入口管所有域名,Host 分流;最省资源prometheus.ergesanbaishou.com:31588
B · 独立 controller(★本环境采用)域名:30990 → 专属 controller → Ingress(独立 class)→ svc:80同 harbor(32588) 模式;端口/规则全隔离;保留 basic auth 等 Ingress 能力prometheus.ergesanbaishou.com:30990
C · svc NodePort 直连节点:30990 → svc(跳过 controller)最轻量,一条 helm upgrade 就有;但绕过 Ingress 层,无 basic authhttp://节点IP:30990(无域名)
# ① 先加仓库(★本机第一次用 ingress-nginx 仓库必须这步!)
#    repo 是"按机器"记的:装 Prometheus 时加的 prometheus-community 不通用;
#    漏了这步 = Error: repo ingress-nginx not found(实测踩坑,已登记第 8 节坑速查)
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm repo list     # 期望看到 ingress-nginx + prometheus-community 两行

# ② 装第三套 ingress-nginx:专属 class=prometheus-nginx,HTTP 固定 30990(同 harbor 32588 模式)
helm upgrade --install ingress-prometheus-nginx ingress-nginx/ingress-nginx \
  -n ingress-nginx \
  --set controller.ingressClassResource.name=prometheus-nginx \
  --set controller.ingressClassResource.controllerValue=k8s.io/ingress-prometheus-nginx \
  --set controller.ingressClassResource.default=false \
  --set controller.service.type=NodePort \
  --set controller.service.nodePorts.http=30990 \
  --set controller.service.nodePorts.https=30490 \
  --set controller.admissionWebhooks.enabled=false \
  --set controller.replicaCount=1
# 三个关键参数:
#   ingressClassResource.name → 只认领 class=prometheus-nginx 的 Ingress,不与共享款(nginx)抢
#   nodePorts.http=30990      → 专属入口;https 顺手固定 30490,以后上证书直接用
#   admissionWebhooks=false   → 新 controller 不装"安检门"(webhook),避开多实例抢校验
#                               的经典坑(那两个 443 svc 是什么 → 见下方 5.6 全景表)

# ③ 等新 controller 就绪(单节点约 30s)
kubectl -n ingress-nginx get pods,svc | grep prometheus
# 期望: pod Running;svc ingress-prometheus-nginx-controller → 80:30990/TCP,443:30490/TCP

# ④ Ingress 切到新 class —— ★前提:服务器上的 yaml 已是新版!(仓库双 clone 实测坑:
#    apply 了旧版 class=nginx,controller 装好了 30990 也死活不通 —— 规则还挂在共享款上)
grep ingressClassName prometheus-ingress.yaml
# 期望输出: prometheus-nginx;若还是 nginx → git pull 或 vim 手动改这一行
kubectl apply -f prometheus-ingress.yaml          # ★ apply 的是 .yaml,不是 .conf!(见下表)
kubectl -n monitoring get ingress prometheus-ingress
# CLASS 列: nginx → prometheus-nginx;换 class = 规则"搬家",31588 上随之失效

# ⑤ 验证专属入口 + 佐证搬家
curl -s -H "Host: prometheus.ergesanbaishou.com" http://10.18.170.34:30990/-/healthy
# 期望: Prometheus is Healthy.
curl -s -H "Host: prometheus.ergesanbaishou.com" -o /dev/null -w '%{http_code}\n' http://10.18.170.34:31588/

5.6 番外:ingress-nginx 命名空间的 5 个 Service 全景(那两个 443 是什么?)

kubectl -n ingress-nginx get svc 装完第三套后会看到 5 个 Service,高频疑问:"下面两个 443 的没开放端口,nginx 是怎么指定的?" —— 答案:它们不是流量入口,是 admission webhook(准入校验"安检门"),只被 API Server 在 kubectl apply Ingress 的那一瞬间集群内部调用(校验注解/snippet 语法对不对),通过即退场,与业务流量零关系,所以 ClusterIP 足够、没 NodePort 属正常:

Service类型 / 端口身份要 NodePort 吗
ingress-nginx-controllerNodePort 80:31588 / 443:30443共享款 controller —— 业务流量入口(k8s-web/hello/xl18z)★要,这就是 31588
ingress-harbor-nginx-controllerNodePort 80:32588 / 443:31443harbor 专属 controller —— 业务流量入口★要(32588)
ingress-prometheus-nginx-controllerNodePort 80:30990 / 443:30490Prometheus 专属 controller(5.5 节新装)★要(30990)
ingress-nginx-controller-admissionClusterIP 443共享款的 admission webhook("安检门")不要 —— API Server 内网调用即可
ingress-nginx-ergesanbaishouClusterIP 443与 harbor controller 同期出现的另一个 webhook不要 —— 同上,非流量入口

一句话:认业务入口只看带 80:xxxxx 的 controller Service;443 的 ClusterIP 是"安检门"。这也正是 5.5 节新 controller 关 admissionWebhooks.enabled=false 的原因 —— 三扇"安检门"会抢校验(多 controller 共存的经典坑)。验证某扇门背后挂谁:

kubectl -n ingress-nginx get svc ingress-nginx-ergesanbaishou -o yaml | grep -A3 selector
kubectl get validatingwebhookconfigurations        # 看集群里有几扇"安检门"
💡 回退与顺序:要回方案 A 只需把 Ingress 的 ingressClassName 改回 nginx 再 apply、外层 NGINX upstream 同步改 31588。注意 30990 在装好 controller 前必然不通,顺序是加仓库 → 装 controller → 切 class → 验端口。
