06 🗄️ 线上数据库磁盘满 —— 止血 → 扩容 → 防复发 处理顺序永远是:先止血保服务,再扩容,最后防复发

数据库是最怕磁盘满的工作负载:一旦写不进 binlog/数据文件,MySQL 会把自己挂起来,业务直接中断。处理顺序永远是先止血保服务,再扩容,最后防复发。

现象确认(告警 90%+ 或已写入失败)

# 1. PVC 使用率告警
kubectl get pvc data-mysql -n prod
NAME        STATUS   VOLUME     CAPACITY   ...
data-mysql  Bound    pvc-8f3..  20Gi

# 2. 进容器看实际占用(看挂载点,不是根分区)
kubectl exec -it mysql-0 -n prod -- df -h /var/lib/mysql
/dev/sdb   20G   18.5G   1.5G  93% /var/lib/mysql

# 3. 是数据涨了还是日志涨了?
kubectl exec -it mysql-0 -n prod -- sh -c 'du -sh /var/lib/mysql/* | sort -rh | head'
# binlog.0000xx  动辄几十 G —— 最常见的元凶
# ibdata1 / ib_logfile0 —— 真实数据/redo,不能删

第一步:止血(只清日志,绝不动数据文件)

# 1. binlog 立刻瘦身:只保留最近 2 天
kubectl exec -it mysql-0 -n prod -- \
  mysql -uroot -p"$PW" -e "PURGE BINARY LOGS BEFORE NOW() - INTERVAL 2 DAY;"

# 2. 慢日志/错误日志轮转(> 清空不换句柄,不断连接)
kubectl exec -it mysql-0 -n prod -- sh -c '> /var/log/mysql/slow.log'

# 3. 临时表/备份残留确认后再删(先看时间戳,别一把梭)

第二步:PVC 在线扩容(业务不中断)

# 前提 1:StorageClass 必须允许扩容
kubectl get sc
NAME       PROVISIONER      ALLOWVOLUMEEXPANSION
nfs-sc     nfs-provisioner  true        ← 允许,继续
local-sc   kubernetes.io/no-provisioner  false   ← 本地盘不支持在线扩,只能迁移

# 直接 patch 目标容量(只能扩大,永远不能缩小!)
kubectl patch pvc data-mysql -n prod \
  -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'

# 盯进度:先等 controller 扩 PV,再等文件系统在线 expand(xfs/ext4 均支持)
kubectl get pvc data-mysql -n prod -w

# 容器内验证(无需重启 Pod)
kubectl exec -it mysql-0 -n prod -- df -h /var/lib/mysql
/dev/sdb   50G   18.5G   32G  37% /var/lib/mysql

第三步:防复发

# 1. binlog 自动过期(my.cnf [mysqld],3 天)
binlog_expire_logs_seconds = 259200
max_binlog_size            = 512M

# 2. 容器日志限制(见 02 磁盘问题 containerLogMaxSize)
# 3. 监控告警阈值提前到 75%,别等 90% 才动手
⚠️ 两条红线:① 永远不要手工删除 /var/lib/mysql 下的 ibdata1、binlog.index 等文件(想清 binlog 用 SQL PURGE);② PVC 扩容只能扩大,缩容不支持;local PV / hostPath 无法在线扩,唯一路径是"新 PVC + 逻辑备份迁移 + 切换"。
