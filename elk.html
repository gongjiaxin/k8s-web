01架构总览与数据流

Pod stdout/stderr
  → loggie DaemonSet(fke-loggie, 22 个 zone=log 节点; K8s 容器自动发现:
    containerd + parseStdout, 读宿主机 /var/log/pods)
  → kafka topic「logs-fke-loggie-topic」(loggie-kafka, 3 broker + 3 controller)
  → logstash(fke-loggie-logstash-logstash-0; group logstash-fke-loggie-consumer)
  → elasticsearch data_stream「logs-fke-loggie-default」(fke-db ns,
    STS elasticsearch-master 3 副本, longhorn PVC 3×100Gi; 落盘 .ds-logs-*)
  → kibana(fke-kibana, 7.17.3, 经 ingress-nginx 暴露)
组件工作负载ns / Helm release版本职责
loggieDS fke-loggie(22/22)kube-infra / fke-loggieloggie-v1.4.0节点上采集容器 stdout
kafkaSTS loggie-kafka(3+3)kube-infra / loggie-kafkakafka 3.6.1日志缓冲/削峰/断流回放
logstashSTS fke-loggie-logstash-logstash-0kube-infra / fke-loggie-logstash7.17.3消费 kafka → 写 ES
elasticsearchSTS elasticsearch-master(3 副本)fke-db /(非 helm 直管)7.17.x存储/检索,data stream
kibanaDeploy fke-kibana-kibanakube-infra / fke-kibana7.17.3查询界面
ingressDS nginx-ingress-nginx-controller(hostNetwork)kube-infra / nginx4.12.2域名入口
💡 从零重建的部署顺序:① ES STS(等 3 节点 green)→ ② kibana + Ingress → ③ kafka → ④ logstash → ⑤ loggie DS(节点打标签 fke.ergesanbaishou.com/zone=log)→ ⑥ LogConfig 采集规则。自底向上,任一层未就绪上层空转。

02部署档案:组件清单 / 关键配置全文

📦 loggie(DaemonSet 采集端)

  • nodeSelector:fke.ergesanbaishou.com/zone=log → 只调度到打该标签的 22 个节点
  • 宿主机挂载:/var/log/pods(采集源)、/var/lib/kubelet/pods(元数据)、/data/loggie-fke-loggie(registry 断点续传)、/run/containerd/containerd.sock(容器发现)
  • 主配置 cm loggie-config-fke-loggie 关键项:
loggie:
  discovery:                    # K8s 容器自动发现模式(无固定 paths)
    enabled: true
    kubernetes:
      cluster: fke-loggie
      containerRuntime: containerd
      dynamicContainerLog: true # 跟随容器日志轮转
      parseStdout: true         # 解析 CRI 日志格式
      typePodFields:            # 事件自动注入字段(Kibana 筛选依据)
        containername: ${_k8s.pod.container.name}
        namespace: ${_k8s.pod.namespace}
        nodename: ${_k8s.node.name}
        podname: ${_k8s.pod.name}
  monitor: { logger: { period: 30s } }   # 每 30s 一条心跳 metric 日志(正常)

🔁 logstash(cm fke-loggie-logstash-logstash-pipeline 全文)

input  { kafka {
         bootstrap_servers => "loggie-kafka.kube-infra.svc.cluster.local:9092"
         topics => ["logs-fke-loggie-topic"]
         group_id => "logstash-fke-loggie-consumer"
         auto_offset_reset => "latest"    # 仅新消费组生效;断流续传按已提交 offset
         codec => "json" } }
filter { json { source => "message" } }
output { elasticsearch {
         hosts => ["http://elasticsearch-master.fke-db.svc.cluster.local:9200"]
         data_stream => true
         data_stream_type => "logs"
         data_stream_dataset => "fke-loggie"
         data_stream_namespace => "default" } }
⚠ 生产注意:线上 output 里还有调试遗留的 stdout { codec => "json" } —— 每条日志双写 stdout 白费 IO,建议删除后 delete pod 重启 logstash 生效。

🗄️ elasticsearch / kibana

  • ES:STS elasticsearch-master(fke-db),svc elasticsearch-master:9200,PVC longhorn 3×100Gi,索引 1 主 1 副本
  • kibana 环境变量:ELASTICSEARCH_HOSTS=http://elasticsearch-master.fke-db.svc:9200
  • Ingress:fke-kibana-kibana(class nginx),host 见第 05 节入口表

03采集范围:哪些日志会进 ELK

⚠ 最重要的认知:不是全集群日志都进 ELK!只有 app + argo 两个 namespace 的日志被采集,其余 40+ ns(kube-system/istio-system/kube-infra/fke-db 等)的日志只能用 kubectl logs 看。
维度实际范围判定依据
节点22 个(标签 fke.ergesanbaishou.com/zone=log)loggie DS nodeSelector
namespace仅 app(全量 pod)+ argo(选择性)LogConfig 选择器
日志类型容器 stdout/stderr(K8s 标准输出)读宿主机 /var/log/pods
文件日志❌ 不采集discovery 模式只走 stdout

快速自查:pod 在 app/argo ns + 节点带 zone=log 标签 + 输出 stdout → 日志在 Kibana;kubectl logs 能看到的 ELK 不一定有(跨 ns 时反向也不成立,ELK 只有 app/argo)。

04存储与保留:存哪 / 多大 / 留多久

问题答案
存到哪ES data stream logs-fke-loggie-default → 索引 .ds-logs-fke-loggie-default-* → fke-db 三个 ES pod 的 longhorn PVC
多少容量3 × 100Gi(300Gi;每条日志 1 主 1 副本双份),当前占用极低(峰值约 7GB 索引数据)
留多久ILM policy logs-7d(7 天自动删除;rollover 约每天 2 个 backing index;实测现存最老索引 ≈3.5 天,以 _cat/indices 实查为准)
要手动清理吗不需要,到期自动删;写入突增(如回放)也会在保留期后自限
# 保留策略三连查(经 elasticsearch-master-0 容器执行)
curl -s 'localhost:9200/_data_stream/logs-fke-loggie-default?pretty' | grep -i ilm_policy
curl -s 'localhost:9200/_ilm/policy/logs-7d?pretty'          # delete 阶段 min_age
curl -s 'localhost:9200/_cat/indices/.ds-logs-fke-loggie-default-*?h=index,docs.count,store.size&s=index'

06日常维护命令速查

🩺 一分钟全链路体检(六条命令)

# 1. 采集端:DS 应 22/22 Running
sudo kubectl -n kube-infra get ds fke-loggie

# 2. 缓冲:kafka broker 应 3 个就绪
sudo kubectl -n kube-infra get sts | grep loggie-kafka

# 3. 消费/写入:logstash pod Running 且日志无 503/rerty 循环
sudo kubectl -n kube-infra logs fke-loggie-logstash-logstash-0 --since=5m | tail -5

# 4. 存储:ES 3 副本 Running
sudo kubectl -n fke-db get pods

# 5. ES 集群:number_of_nodes=3 且 status=green
sudo kubectl -n fke-db exec elasticsearch-master-0 -- \
  curl -s 'localhost:9200/_cluster/health?pretty' | grep -E 'number_of_nodes|status'

# 6. 写入量:最新索引 docs.count 应持续增长
sudo kubectl -n fke-db exec elasticsearch-master-0 -- \
  curl -s 'localhost:9200/_cat/indices/.ds-logs-fke-loggie-default-*?h=index,docs.count&s=index' | tail -3

🔧 常用运维操作

# 重启 logstash(改完 pipeline cm 后必须)
sudo kubectl -n kube-infra delete pod fke-loggie-logstash-logstash-0

# 查看/编辑 loggie 采集规则
sudo kubectl -n kube-infra get logconfig
sudo kubectl -n kube-infra edit logconfig 

# 查 logstash 消费 lag(等价 kafka-ui)
sudo kubectl -n kube-infra exec loggie-kafka-0 -- \
  kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group logstash-fke-loggie-consumer

# ES 磁盘水位(任一节点 >85% 会停写入新索引,>95% 全停,read_only)
sudo kubectl -n fke-db exec elasticsearch-master-0 -- \
  curl -s 'localhost:9200/_cat/allocation?v'

# Longhorn 卷健康(ES PVC)
sudo kubectl -n longhorn-system get volumes | grep -v healthy
⚠ ES 只读应急(磁盘水位触发后):清理磁盘后需手动解锁:curl -XPUT 'localhost:9200/_all/_settings' -H 'Content-Type:application/json' -d '{"index.blocks.read_only_allow_delete": null}'(经 master-0 容器执行)。

🚨 告警建议(当前无告警,建议尽快补上)

告警项条件为什么
ES 节点数number_of_nodes != 3 持续 5 分钟本次事故正是 master-2 掉队 87 天无人发现 → 日志断流
日志零写入最新索引 docs.count 30 分钟无增长任何一层断裂的最终共同表征,一票否决式信号
kafka 消费滞后logstash group lag > 10 万 或持续增长 30 分钟写入跟不上/ES 不可用的前兆
logstash 错误循环日志出现 503 / retry 循环svc 后端有坏节点的指纹(本次根因的直接表象)
Longhorn 卷非 healthyrobustness != healthy / 卷 degraded存储层是本次根因;healthy 也不排除只读降级,配合节点数告警双保险

08真实故障复盘 + 常见故障速查

💥 案例:Longhorn 卷只读 → 日志断流 2 天(2026-11 修复)

环节事实
根因87 天前 ES master-2 的 longhorn 卷降级为只读(frontend RO 不会自愈),ES FsHealthService 报错掉出集群,但 pod 仍 Running
表象svc 轮询 1/3 请求打到坏节点 → 503 → logstash 停写 2 天;Kibana 查不到新日志
修复delete pod elasticsearch-master-2(软重启=卷卸载重挂 RW)→ 集群回 3 节点 green,零数据损失,kafka 积压自动回放
要点① STS 3/3 Running ≠ 应用健康;② "随机 1/N 请求失败" = svc 后端有坏节点指纹;③ data_stream 回放写入当前索引但保留原 @timestamp → 某些日期索引 0 文档 ≠ 丢数据

server {
    listen 80;
    server_name new-fke-kibana.ergesanbaishou.com;

    location / {
        proxy_pass http://10.18.51.120:30081;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_set_header Upgrade $http_upgrade;
