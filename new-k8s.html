01背景与集群现状

项目现状
集群new-k8s-fke:m1 控制面 + n1/n2/n3 提供存储(master 不跑存储,布局规范)
Longhornv3.12 系列 UI(v1.12.1),3 存储节点 × 292.26 Gi = 877 Gi,默认预留 30%(263 Gi)
卷4 个卷全部 3 副本(每节点 4 副本 ×3 = 12),全部健康,挂一台节点不降级
UI Servicelonghorn-frontend,ClusterIP :80 → 2 × longhorn-ui Pod(容器端口 8000)

⚠ 前提认知:Longhorn 没有任何内置账号体系(直到最新的 1.13 也是),官方文档的认证方案就是在前面加一层代理认证。UI 拿到访问权 = 存储管理员:删卷、detach(业务直接崩溃)、清盘、改副本策略,全程无确认。所以"开端口"必须连带"加认证 + 限源",三件事是一件套。

02目标架构(一图流)

浏览器 https://new-longhorn.ergesanbaishou.com
   │ ① DNS 解析到 NGINX 机器
   ▼
外层 NGINX(443 TLS 终止 + Basic Auth + upstream 多节点轮询)
   │ ② proxy_pass → 任意节点 IP:30010
   ▼
═══════ K8S 集群边界(每个节点都在 30010 监听)═══════
   │ ③ kube-proxy(iptables/ipvs NAT 转发)
   ▼
Service longhorn-frontend(NodePort 30010 → 80)
   ▼
longhorn-ui Pod ×2(n1/n2,容器端口 8000)
💡 三个关键认知:① NodePort = 所有节点都监听该端口,流量打到哪个节点都行,kube-proxy 自动转到真正跑 Pod 的节点,访问不限于 Pod 所在节点;② proxy_pass 写死单节点 = 单点故障,必须用 upstream 多节点轮询;③ 永远不要写 ClusterIP(集群外路由不到)和 Pod IP(会变)。

03第①步:确认 Service 端口定义(命名端口坑)

patch 之前必须先看清 ports 的真实定义 —— merge patch 会整体替换 ports 列表,字段抄错一个,转发就断。

kubectl -n longhorn-system get svc longhorn-frontend -o yaml | grep -B2 -A6 "ports:"

# 本集群实际输出:
#   ports:
#   - name: http
#     port: 80
#     protocol: TCP
#     targetPort: http        ← 注意:命名端口(字符串),不是数字!
⚠ 最大的坑:targetPort 是命名端口:targetPort: http 引用的是容器端口名而不是数字 8000。patch 的 JSON 里必须写成字符串 "targetPort":"http",且 name / protocol 原样保留 —— 写成 8000 或漏掉 name 都可能破坏转发。这就是"网上教程直接抄 targetPort:8000 会翻车"的原因(老版本 Longhorn 才是数字端口)。

04第②步:Service 改 NodePort(patch / 验证 / 回退)

方式 A:自动分配端口(30000–32767 随机)

kubectl -n longhorn-system patch svc longhorn-frontend -p '{"spec":{"type":"NodePort"}}'

方式 B:指定固定端口(推荐,本例 30010;字段按 03 节实际输出原样保留)

kubectl -n longhorn-system patch svc longhorn-frontend -p \
  '{"spec":{"type":"NodePort","ports":[{"name":"http","port":80,"protocol":"TCP","targetPort":"http","nodePort":30010}]}}'

✅ 验证

kubectl -n longhorn-system get svc longhorn-frontend
# 期望 PORT(S) 列显示:80:30010/TCP

# 任意节点本机自测(验证 kube-proxy 转发链路)
curl -sI --connect-timeout 5 http://127.0.0.1:30010 | head -1
# 期望:HTTP/1.1 200 OK

↩️ 回退(恢复 ClusterIP)

kubectl -n longhorn-system patch svc longhorn-frontend -p \
  '{"spec":{"type":"ClusterIP","ports":[{"name":"http","port":80,"protocol":"TCP","targetPort":"http"}]}}'
💡 提醒:① 访问用任意节点 IP 均可(原理见 02 节);② 若 Longhorn 是 Helm 装的,直接 patch 后将来 helm upgrade 可能把类型改回去 —— 要么固化到 values,要么升级时留意;kubectl manifest 安装则无此问题。

05第③步:NGINX 反向代理(多节点轮询,拒绝单点)

在 NGINX 机器上新增站点配置(/etc/nginx/conf.d/longhorn.conf),upstream 挂全部节点 —— NGINX 默认轮询(round-robin),一台挂了自动切下一台:

# 节点 IP 以 kubectl get nodes -o wide 为准(下面是示例)
upstream longhorn_ui {
    server 10.18.51.11:30010 max_fails=2 fail_timeout=5s;   # m1
    server 10.18.51.12:30010 max_fails=2 fail_timeout=5s;   # n1
    server 10.18.51.13:30010 max_fails=2 fail_timeout=5s;   # n2
}

server {
    listen 80;
    server_name new-longhorn.ergesanbaishou.com;   # ★ 必须和下面 443 块一致!
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name new-longhorn.ergesanbaishou.com;

    ignore_invalid_headers off;
    client_max_body_size 0;
    proxy_buffering off;
    proxy_request_buffering off;

    location / {
        auth_basic           "Longhorn UI";            # 06 节加密码时启用
        auth_basic_user_file /etc/nginx/.htpasswd;

        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 300;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        chunked_transfer_encoding off;

        # 节点故障自动重试下一台(配合 upstream 使用)
        proxy_next_upstream error timeout http_502 http_503 http_504;

        proxy_pass http://longhorn_ui;
    }
}
# 生效
nginx -t && nginx -s reload

# 验证:NGINX 机器上逐个 curl 节点,三个都 200 才算高可用成立
curl -sI --connect-timeout 5 http://10.18.51.11:30010 | head -1
curl -sI --connect-timeout 5 http://10.18.51.12:30010 | head -1
curl -sI --connect-timeout 5 http://10.18.51.13:30010 | head -1
⚠ 实测踩过的坑:① 域名一致性 —— 80 跳转块的 server_name 与 443 块不一致时,http 跳到 https 后找不到匹配 server,落到默认站点(表现为 502/404/打开别的站);② proxy_pass 写死单节点是初版写法,该节点一重启就 502 —— upstream 轮询是修正版;③ proxy_next_upstream 别漏,否则故障节点摘除不果断;④ ★ proxy_set_header Host $http_host; 透传域名永远是反代的灵魂行。

06第④步:Basic Auth 加密码(NGINX 层认证)

Longhorn 没有内置账号体系,认证放在 NGINX 层 —— 三步完成,全程平滑不影响业务:

# ① NGINX 机器上安装工具 + 创建密码文件(-c 新建;第二个用户起不要带 -c)
apt-get install -y apache2-utils
htpasswd -c /etc/nginx/.htpasswd admin          # 交互输入两次密码

# 不装 apache2-utils 的一行替代:
# printf "admin:$(openssl passwd -apr1 '你的密码')\n" > /etc/nginx/.htpasswd

# ② 443 server 的 location / 里加两行(05 节配置已含):
#    auth_basic           "Longhorn UI";
#    auth_basic_user_file /etc/nginx/.htpasswd;

# ③ 检查并平滑重载(不断连接)
nginx -t && nginx -s reload

✅ 验证

curl -sI https://new-longhorn.ergesanbaishou.com | head -1                # 期望 401
curl -sI -u admin:密码 https://new-longhorn.ergesanbaishou.com | head -1   # 期望 200
💡 实践建议:① 测试 / 线上环境账号分开(各自一份 htpasswd),避免泄露一个打穿两个;② 顺手把配置里注释掉的 access_log 打开,出问题有据可查;③ 浏览器会自动缓存 Basic Auth 凭据,Ajax/WebSocket 请求都会带上,Longhorn UI 工作正常。

07第⑤步:防火墙限源(堵住 NodePort 旁路)

⚠ 光加 NGINX 密码还不够!链路是"浏览器 → NGINX → 节点:30010",而 NodePort 30010 本身是无认证裸奔的 —— 知道节点 IP 的人可以完全绕过 NGINX 直连 http://节点IP:30010。必须把 30010 的来源限制为只有 NGINX 那台机器。
# 每个节点上执行(或等效的云安全组规则):
ufw allow from  to any port 30010 proto tcp
ufw deny 30010/tcp

# 验证:在 NGINX 机器上 curl 节点 30010 → 通;
#       在其他任意机器上 curl → 应该不通(timeout/refused)
💡 最终安全形态:域名 → TLS + Basic Auth → NGINX → 只对 NGINX 开放的 NodePort → UI。四层各司其职:加密、认证、高可用转发、来源白名单。

08502 Bad Gateway 排查实录(决策树)

502 说明 NGINX 本身正常,NGINX → 节点:30010 这一跳失败了。实测时还发现一个有用的旁证:kubectl logs 看 UI Pod 没有访问日志 —— 说明流量根本没到 Pod(没收到请求自然没日志)。

第一步:看 NGINX 错误日志,直接锁定方向

tail -n 30 /var/log/nginx/error.log
error.log 关键字含义排查方向
connect() failed (111: Connection refused)节点上 30010 没人监听端口不对 / 没改成 NodePort / 防火墙 REJECT
connect() failed (110: Connection timed out)包被丢弃节点防火墙 DROP / 网络不通
no live upstreamsupstream 全部节点被标记挂了同上,或 upstream 配置错
host not found in upstreamupstream 名字解析失败NGINX 配置本身的问题

第二步:分层 curl,找到断点在哪一层

# ① NGINX 机器 → 各节点(换成本环境 upstream 里的真实 IP)
curl -sv --connect-timeout 5 http://节点IP:30010/ -o /dev/null 2>&1 | tail -n 5
#   200 → 节点正常,问题在 NGINX 配置(upstream 名/proxy_pass/没 reload)
#   refused → 端口不对或被 REJECT;timeout → 防火墙 DROP/路由不通

# ② 节点本机 → 自测 kube-proxy(SSH 到任一节点)
curl -sI --connect-timeout 5 http://127.0.0.1:30010 | head -1
#   200 → kube-proxy 正常,问题在"NGINX 机 → 节点"之间的网络/防火墙

# ③ 节点 → 直连 Pod,绕过 Service 验证应用本身(8000 是容器端口)
curl -sI --connect-timeout 5 http://10.244.253.5:8000 | head -1
#   200 → Pod 正常,问题在 Service/kube-proxy 层,看第三步

第三步:②失败时,检查 Service 转发链路

kubectl -n longhorn-system get ep longhorn-frontend     # endpoints 应有 2 个 Pod IP
kubectl -n kube-system get pods -o wide | grep kube-proxy   # kube-proxy 健康?
iptables-save 2>/dev/null | grep 30010 | head -5            # iptables 模式:有转发规则?
ipvsadm -ln 2>/dev/null | grep -A3 30010                    # ipvs 模式
💡 实测结论:本次 502 的两大高发原因是 ① 实际 NodePort 和 NGINX 里写的不一致(自动分配是随机的,先 get svc 核对);② NGINX 机器到节点 30010 被防火墙拦(refused=端口没开,timeout=被丢包)。先跑第一步的 error.log,基本一眼定位。

10安全清单 & 线上(fke)同款隐患加固

✅ new-k8s 本次收尾自查清单

  • 认证:Basic Auth 生效(无凭据 401,带凭据 200)
  • 限源:30010 只对 NGINX 机器开放,其他来源全部拒绝
  • TLS:https 强制(80 → 301 → 443)
  • 高可用:upstream 三节点轮询,单节点故障自动切换
  • 回退预案:04 节的 ClusterIP 回退命令已验证可用

🚨 线上 fke 集群的同款隐患(排查 fke 时发现)

fke 线上集群的 longhorn-frontend 是 80:30010/TCP 的 NodePort,无任何认证,已暴露 447 天 —— 拿到节点 IP 的人可以直接管理线上存储(删卷 / detach / 清盘)。建议四步处置:

# ① 先确认有没有人在用(避免误伤)
sudo kubectl -n longhorn-system get svc longhorn-frontend
sudo grep -r "30010" /etc/nginx/ 2>/dev/null          # 有没有反代引用

# ② 立即用防火墙止血(只放行白名单,或直接 deny)
ufw deny 30010/tcp

# ③ 中期:改回 ClusterIP 关门,统一走带认证的域名
kubectl -n longhorn-system patch svc longhorn-frontend -p '{"spec":{"type":"ClusterIP"}}'

# ④ 溯源:确认暴露期间是否被人动过
kubectl -n longhorn-system get events --sort-by=.lastTimestamp | tail -n 30
# 卷数量、副本数是否有异常变化;必要时看 volume 的 snapshot/创建时间
⚠ 顺带排查:同在 fke 的 Argo Workflows server(argo-server.ergesanbaishou.com)疑似匿名可访问(未验证)—— 匿名能进 = 能提交 Workflow = 能在集群里跑任意容器,风险比 Longhorn UI 更高,值得优先确认。详见 线上 ArgoCD 部署档案第 07 节待办清单。
