01先分清:ArgoCD ≠ Argo Workflows(本次排坑起点)

两个项目同属 Argo 家族,名字像、Logo 像、版本号格式像(都是 v3.x),但是两个完全不同的软件。本次排坑的真实过程:先用 get ns | grep -i argo 只找到 argo 这个 namespace(里面是 Argo Workflows),一度误判"线上没装 ArgoCD" —— 实际上 ArgoCD 装在 kube-infra,ns 名字不含 argo,换 get deploy -A | grep -i argocd 才现形。

维度Argo Workflows(线上 ns:argo)ArgoCD(线上 ns:kube-infra)
定位任务编排引擎:在 K8S 里跑批处理流水线(DAG/步骤)GitOps 持续交付:把 Git 里的 YAML/Helm 同步到集群
干的事跑 Job:数据转换、质检、标注、ETL、训练管部署:应用该跑什么版本、漂了自动拉回
触发手动提交 / 定时 / 事件触发Git 仓库一变就自动同步
一句话"帮我在集群里跑一批任务""帮我把集群变成 Git 描述的样子"

🔍 打开 UI 怎么一眼区分

特征ArgoCDArgo Workflows
左侧主菜单Applications、Settings、User InfoWorkflows、Workflow Templates
状态指标SYNC STATUS(Synced/OutOfSync)+ HEALTH STATUS(Healthy/Degraded/Missing)只有工作流状态(Running/Succeeded/Failed)
条目内容Git 仓库、Target Revision、Path、Destination、Last Sync步骤图、耗时、日志
💡 两者冲突吗?可以同时共存吗?完全不冲突 —— 它们是两个独立开源项目,组件名(argocd-* / argo-*)、CRD(Applications / Workflows)、数据库与配置互不相干,装在不同(甚至相同)namespace 互不影响。本集群就是共存实证:kube-infra 里 ArgoCD 管交付,argo ns 里 Workflows 管数据流水线。业界常见的"Argo 全家桶"(ArgoCD + Workflows + Rollouts + Events)也全部这样共存,需要时还能联动:ArgoCD 把 WorkflowTemplate 纳入 GitOps 管理、Argo Events 事件触发 Workflows 跑批。唯一要注意的就是别把名字搞混(见 01 节开头)。

  • 规模:75 个应用(get applications -A | wc -l = 76,含表头),按 Project 分组:kube-infra(基础设施)/ app(业务)/ livekit 等

09第一步:开发机(Ubuntu)下载全部资源

需要下载 3 类资源:Chart 包、argocd CLI、容器镜像。镜像清单不是拍脑袋列的 —— 用本地渲染一次性拿全(该命令不联网,服务器上也能跑):

# 列出整套 Chart 渲染后需要的全部镜像(★ 离线安装必备命令)
helm template argocd ./argo-cd-10.17.2.tgz -n argocd | grep -E "image:" | sort -u

# 实测输出(3 个):
#   quay.io/argoproj/argocd:v3.6.1                        ← server/repo-server/controller/job 共用
#   ecr-public.aws.com/docker/library/redis:8.6.4-alpine  ← redis
#   ghcr.io/dexidp/dex:v2.46.1                            ← dex(SSO)
# ① Chart 包 + CLI(GitHub Release)
curl -LO https://github.com/argoproj/argo-helm/releases/download/argo-cd-10.17.2/argo-cd-10.17.2.tgz
curl -LO https://github.com/argoproj/argo-cd/releases/download/v3.6.1/argocd-linux-amd64

# ② 三个镜像拉取并打包
docker pull quay.io/argoproj/argocd:v3.6.1
docker pull ecr-public.aws.com/docker/library/redis:8.6.4-alpine
docker pull ghcr.io/dexidp/dex:v2.46.1

docker save -o all-images.tar \
  quay.io/argoproj/argocd:v3.6.1 \
  ecr-public.aws.com/docker/library/redis:8.6.4-alpine \
  ghcr.io/dexidp/dex:v2.46.1

# ③ 校验(与服务器端 sha256sum 对比,防止传输截断)
sha256sum argo-cd-10.17.2.tgz
ls -lh argo-cd-10.17.2.tgz argocd-linux-amd64 all-images.tar
💡 ecr-public 拉不动时的替代:Docker Hub 有同款镜像,拉完改 tag 即可:docker pull redis:8.6.4-alpine && docker tag redis:8.6.4-alpine ecr-public.aws.com/docker/library/redis:8.6.4-alpine(内容相同,K8s 只认 tag 名)。dex 若拉不动且不需要 SSO,可在 values 里 dex.enabled=false 干脆不装。

10第二步:上传 + 全节点镜像导入(★ 本次最大坑)

📤 上传到 m1

# 开发机执行
scp argo-cd-10.17.2.tgz argocd-linux-amd64 all-images.tar \
    root@10.18.51.120:/root/k8s-install/argocd/
⚠ 核心坑:ctr import 只导入"本机"!ctr -n k8s.io images import 只把镜像写进当前这台机器的 containerd。K8s Pod 可能调度到任意节点,哪个节点没镜像、哪个节点就 ImagePullBackOff(外网又拉不动)。6 台节点必须全部导入。

📥 m1 上分发导入全部 6 节点(需 SSH 免密;IP 版)

cd /root/k8s-install/argocd

# m1 自己导入
ctr -n k8s.io images import all-images.tar

# 分发其余 5 台(m2/m3/n1/n2/n3)
for node in 10.18.51.121 10.18.51.122 10.18.51.123 10.18.51.124 10.18.51.125; do
  echo ">>> $node"
  scp all-images.tar root@$node:/tmp/
  ssh root@$node "ctr -n k8s.io images import /tmp/all-images.tar && rm /tmp/all-images.tar"
done

# 验证:每台都应输出 3 行镜像(argocd/redis/dex)
for node in 10.18.51.120 10.18.51.121 10.18.51.122 10.18.51.123 10.18.51.124 10.18.51.125; do
  echo ">>> $node"
  ssh root@$node "ctr -n k8s.io images ls -q | grep -E 'argocd|redis|dex'"
done
# 顺手装好 CLI
install -m 555 argocd-linux-amd64 /usr/local/bin/argocd
argocd version --client   # 确认输出 v3.6.1
💡 为什么是 -n k8s.io:kubelet 使用 containerd 的 k8s.io namespace 存镜像;不带此参数导入会进 default namespace,Pod 照样找不到镜像。长期方案可搭 Harbor 私仓或给 containerd 配镜像加速,免去逐节点导入。

11第三步:helm 本地包安装 + pre-install 超时排坑

helm install argocd ./argo-cd-10.17.2.tgz \
  --namespace argocd \
  --create-namespace \
  --timeout 10m

💥 现场报错(只导入了 m1 镜像时)

Error: INSTALLATION FAILED: failed pre-install: 1 error occurred:
  * timed out waiting for the condition

含义:Chart 有个 pre-install Hook Job —— argocd-redis-secret-init(执行 argocd admin redis-initial-password 生成 Redis 初始密码),它 5 分钟内没跑完。排查三连:

# ① Pod 调度到了哪个节点?状态如何(关键看 NODE 列!)
kubectl get pods -n argocd -o wide
# 实测:argocd-redis-secret-init-7gszb  0/1  ImagePullBackOff  ...  new-k8s-fke-n3   ← 调度到了 n3!

# ② 事件里看拉镜像的真实报错
kubectl get events -n argocd --sort-by=.lastTimestamp | tail -30
# 实测:Failed to pull image "quay.io/argoproj/argocd:v3.6.1":
#       dial tcp 18.211.141.190:443: i/o timeout   ← n3 节点拉外网超时

# ③ 排除文件损坏:开发机/服务器两端 sha256sum 对比(实测一致)
⚠ 根因链:镜像只导入 m1 → Hook Pod 被调度到 n3 → n3 本地无镜像且外网不通 → ImagePullBackOff → helm 等 hook 完成直到超时。报错发生在 pre-install 阶段时,先查 Hook Job 的 Pod,不要怀疑网络或 Chart 本身。

✅ 修复:全节点导入镜像(见第 10 节)后清理重装

helm uninstall argocd -n argocd
kubectl delete jobs,pods -n argocd --all --ignore-not-found

helm install argocd ./argo-cd-10.17.2.tgz \
  --namespace argocd --create-namespace --timeout 10m

kubectl get pods -n argocd -w

12第四步:NodePort + insecure(Nginx 前置必配,30443 撞号坑)

独立 Nginx(new-k8s-nginx-1)在集群外,访问不了 ClusterIP(10.104.254.21),因此要把 argocd-server 改成 NodePort;同时 TLS 由 Nginx 终结,Argo CD 必须开 insecure,否则会出现重定向循环。

📄 /root/k8s-install/argocd/argocd-ingress.yaml(最终版全文)

global:
  domain: new-argocd.ergesanbaishou.com   # UI 内生成链接用的域名
configs:
  params:
    server.insecure: true            # TLS 交给 Nginx,避免重定向循环
server:
  service:
    type: NodePort
    nodePortHttp: 30043              # Nginx upstream 反代的就是它
    nodePortHttps: 30444             # insecure 模式用不到,但 Service 会分配,必须给空闲值!

💥 撞号坑:只写 nodePortHttp 时必报错

# 只配了 nodePortHttp: 30043 就执行 upgrade,报:
Error: UPGRADE FAILED: cannot patch "argocd-server" with kind Service:
Service "argocd-server" is invalid: spec.ports[1].nodePort:
Invalid value: 30443: provided port is already allocated

# 原因:chart 的 nodePortHttps 有默认值 30443,与集群已有服务撞号
# 修复:两个端口都显式指定(30043 + 30444)
# 查看全集群已占用的 NodePort(选端口前先跑这个,避开 30010/30880/30443)
kubectl get svc -A -o custom-columns='NS:.metadata.namespace,SVC:.metadata.name,PORTS:.spec.ports[*].nodePort' | grep -v '<none>'

# 升级(本地 tgz,不联网)
helm upgrade argocd ./argo-cd-10.17.2.tgz -n argocd -f argocd-ingress.yaml

# 验证:TYPE 变 NodePort,80 端口后面出现 30043
kubectl get svc argocd-server -n argocd
# argocd-server   NodePort   10.104.254.21   <none>   80:30043/TCP,443:30444/TCP

# 在 Nginx 机器上验证后端连通(期待 HTTP/1.1 200 OK)
curl -I http://10.18.51.123:30043/
💡 30043/30444 是自选空闲端口:K8s NodePort 允许范围 30000-32767,实测避开了 Longhorn 的 30880/30010。改别的端口记得同步改 Nginx upstream 和这里。

13第五步:Nginx 反代 new-argocd.ergesanbaishou.com(完整 conf)

在 new-k8s-nginx-1 上创建 /etc/nginx/conf.d/new-argocd.conf(风格与 new-longhorn.conf 一致:多节点 NodePort 轮询 + 泛域名证书,但有三处关键差异,见下方表格):

# WebSocket 升级支持(Argo CD UI 的日志流 / Web 终端需要)
# 变量名加前缀,避免与其他 conf 里的 map 重名冲突
map $http_upgrade $argocd_connection_upgrade {
    default upgrade;
    ''      close;
}

# 所有 worker 节点都监听 30043,加进来做轮询
upstream argocd_server {
    server 10.18.51.123:30043 max_fails=2 fail_timeout=5s;  # n1
    server 10.18.51.124:30043 max_fails=2 fail_timeout=5s;  # n2
    server 10.18.51.125:30043 max_fails=2 fail_timeout=5s;  # n3
}

server {
    listen 80;
    server_name new-argocd.ergesanbaishou.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name new-argocd.ergesanbaishou.com;

    ssl_certificate     /etc/nginx/ssl/_.ergesanbaishou.com.pem;    # 泛域名证书
    ssl_certificate_key /etc/nginx/ssl/_.ergesanbaishou.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;

    ignore_invalid_headers off;
    client_max_body_size 0;
    proxy_buffering off;
    proxy_request_buffering off;

    location / {
        # Argo CD 自带账号体系,无需像 Longhorn 那样加 auth_basic

        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;   # insecure 模式下 ArgoCD 依赖此头

        # WebSocket 支持(与 Longhorn 的 Connection "" 不同!)
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $argocd_connection_upgrade;

        # 长超时: gRPC / Web 终端 / 日志流
        proxy_connect_timeout 300;
        proxy_read_timeout    300;
        proxy_send_timeout    300;

        # 节点故障时自动重试下一台
        proxy_next_upstream error timeout http_502 http_503 http_504;

        proxy_pass http://argocd_server;
    }
}

🔧 与 new-longhorn.conf 的三处关键差异(不能照抄)

配置项LonghornArgo CD原因
Connection 头""(纯 keepalive)$argocd_connection_upgrade(map)Argo CD 需要 WebSocket 升级(UI 日志流/Web 终端)
X-Forwarded-Proto可有可无必需insecure 模式下 Argo CD 靠它生成正确的跳转链接
proxy_read_timeout300(够用)300(必须有)gRPC 长连接不能被中途切断

🔄 配置文件修改怎么生效?(无 CI 场景:数据库/中间件改参数)

灵魂拷问:"数据库这种不用打包的,改完 values 点 Sync,配置是复制进 pod 还是新建 pod 复制?"——都不是。配置从不"进 pod",机制是 ConfigMap 投影。

无 CI 的流程(CI 只是往 Git 塞东西的机器人,没有它就手动塞):

改 values(yaml)→ git push → ArgoCD 标黄(OutOfSync)→ Sync
→ ArgoCD helm 渲染最终 YAML → kubectl apply 改的是【集群对象】:
   ConfigMap(配置) / StatefulSet(工作负载) —— 从不直接碰 pod!

配置的真实去向:apply 后配置变成集群里的 ConfigMap 对象(存 etcd);kubelet 把它以挂载投影方式呈现在容器路径下(内存盘实时投影,不是拷贝副本)。pod 里的 /etc/xxx.conf 本质是 ConfigMap 的"直播画面"。

你改了什么pod 结果怎么生效
配置内容(卷挂载方式)不重建kubelet 约 1 分钟自动刷新容器内文件;但应用多半要重启才读新配置(nginx 要 reload,pg/redis 只在启动时读一次)
配置内容(环境变量方式)必须重建env 在 pod 出生时一次性固化,后改 ConfigMap 无效
配置内容(chart 带 checksum 注解)自动滚动重建(主流做法)配置 hash 算进 pod 注解 → pod 模板变 → 自动重建强制生效
资源限额 / 镜像 / 副本数滚动重建StatefulSet/Deployment 的 spec 直接变了
★ 数据库类 pod 重建不丢数据:数据在 PVC、配置在 ConfigMap,pod 只是可抛弃的"计算外壳"——新 pod 起来后重新挂回同一个 PVC(数据都在)+ 挂新 ConfigMap(参数是新的),读新配置启动。注意:单副本 + 独占 RWO 盘的(如 influxdb)必须用 Recreate 策略先删旧再起新,否则新 pod 抢不到盘、卡死 ContainerCreating。

👥 多用户:创建用户并只授权指定 App(开发自助发布)

场景:开发 dev1 只能操作 qingfeng-test-web 这一个应用(可 Sync/回滚),删不了、碰不了别人的应用;其他未授权用户只读。全程不用发 kubeconfig。

第①步:创建本地用户(argocd-cm)

kubectl -n argocd edit configmap argocd-cm
# 在 data: 段增加一行(多个用户就多行):
#   data:
#     accounts.dev1: apiKey,login      # 允许 UI 登录 + API/CLI
#     # accounts.dev1.enabled: "false" # 以后想禁用加这行

# 生效(重建 server Pod,约 10 秒)
kubectl rollout restart deploy/argocd-server -n argocd

第②步:给 dev1 设密码(admin 登录后执行)

argocd login 10.18.51.123:30043 --username admin --insecure --grpc-web
argocd account update-password --account dev1   # 提示输入 dev1 的新密码
argocd account list                            # 确认账号已存在
⚠ 实测踩坑:rpc error: current password does not match —— 第一个提示要的是 admin 当前明文密码(敏感操作当场复验,和 login 用的同一个),手输易错建议粘贴。若 admin 密码记混了,重置:argocd account bcrypt --password '新密码' 生成 hash → kubectl -n argocd patch secret argocd-secret -p '{"stringData":{"admin.password":"<hash>","admin.passwordMtime":"2026-11-12T09:00:00Z"}}' → 重启 server → argocd relogin 再设。

第③步:授权到指定 App(argocd-rbac-cm)

新建集群打开是全空默认态(policy.csv: ""、policy.default: "")。填法:policy.csv 从 "" 改成竖线 |(竖线后不能有任何字符),策略行缩进 4 空格;matchMode/scopes/metadata 原有的一律不动:

kubectl -n argocd edit configmap argocd-rbac-cm
# policy 资源格式:<project>/<application>(default 是 AppProject 名,不是 namespace!)
data:
  policy.csv: |                        # "" → | 竖线块,下面每行缩进 4 空格
    # 定义"应用开发者"角色:只对这一个 App 有 查看/同步/更新(回滚) 权限
    p, role:app-dev, applications, get,    default/qingfeng-test-web, allow
    p, role:app-dev, applications, sync,   default/qingfeng-test-web, allow
    p, role:app-dev, applications, update, default/qingfeng-test-web, allow
    # 没给 delete → 删不了
    g, dev1, role:app-dev               # 用户入组(可加多人:dev1、dev2...)
  policy.default: role:readonly        # "" → 兜底:未授权的人只读
  policy.matchMode: glob                # ↓ 原有两行,不动
  scopes: '[groups]'
# 改完同样 rollout restart deploy/argocd-server -n argocd 生效

第④步:验证

# admin 视角:模拟 dev1 的权限(不用真登录)
argocd account can-i sync applications default/qingfeng-test-web --account dev1
# → yes;换个 App 名或 delete 动作 → no

# dev1 视角:登录后自助闭环
argocd login 10.18.51.123:30043 --username dev1 --insecure --grpc-web
argocd app list                       # 未授权 App 也在列(只读),动手会 Permission denied
argocd app sync qingfeng-test-web     # 自己发版
argocd app rollback qingfeng-test-web 3   # 自己回滚
# UI 同理:浏览器登录 → Applications → Sync / History → Rollback 全自助

➕ 以后每分配一个 App / 一个开发(固定套路)

分配 = 给 role:app-dev 加条目,角色定义永不重写:

# 新 App = 照抄三行 p 改名(get/sync/update);新同事 = 加一行 g
kubectl -n argocd edit configmap argocd-rbac-cm
kubectl rollout restart deploy/argocd-server -n argocd
argocd account can-i sync applications default/<新App> --account dev1   # yes 才算数
粒度写法效果适用
default/<app> 逐个加三行精确到单 App现阶段推荐,一目了然
default/*default 项目下全部 App 全权(含删)太宽,不建议
proj/qingfeng/*整个 AppProject 内全部 AppApp 多了的正道:建专属 project,一行授权全组

可见性说明:policy.default: role:readonly 下,未授权的 App 依旧可见但只读——分配只影响"能不能动手";要连看都隔离,得用 AppProject 把应用建进专属项目。

常用对象说明
role:admin / role:readonly内置角色:全权 / 只读
g, dev1, role:app-dev用户入组;也可给 OIDC 组整组授权 g, dev-team, role:app-dev
AppProject更硬的边界:专属项目限定仓库/目标 ns/集群,角色只作用于 proj/* 内的应用
SSO(Dex)企业账号(OIDC/LDAP)统一登录,本地用户只是轻量方案
💡 一句话总结 ArgoCD 的存在意义:把"集群现在长什么样"从一次性命令和人脑记忆,变成 Git 里一份可版本化、可 review、可回滚、可审计的文件 —— 集群只是这份文件的投影,歪了就拉回。kubectl 是遥控器(谁拿到都能按,按完不留痕);ArgoCD 是自动驾驶 + 行车记录仪(路线=Git,偏航自动回正,全程录像,每个乘客只能按自己车门上的按钮)。
