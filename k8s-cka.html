C1考试概览:17 道题都考什么?

CKA(Certified Kubernetes Administrator)是 CNCF / Linux Foundation 推出的基于实操的认证 —— 不是选择题,而是要求你在真实的 Kubernetes 集群环境中解决实际问题:考试通常包含 17 道题目,限时 2 小时完成。

项说明
认证机构CNCF / Linux Foundation
考试语言英文 / 简体中文 —— 在 PSI 预约考试时选择,与报名渠道无关(中文站 training.linuxfoundation.cn 报名只是付款方式不同,考试全球同一套);预约后不能换、考试中不能切。CKS 仅有英文。技术英语句式重复度高,主流建议选英文 + 当场查官方文档;英文吃力选中文完全可行
考试形式全程实操(命令行 + 真实多节点集群),无选择题
题量 / 时长17 题 / 2 小时(平均每题约 7 分钟)
考试环境内嵌终端 + 多个集群(每题可能要求切换 context)
题目形态题库变体:命名空间、标签、版本号等参数每次变化,核心知识点和解题思路不变

分数怎么算:满分 100,及格 66

项说明
满分100 分
及格线66 分(2020-09 起从 74% 降下来的,沿用至今)
单题分值官方不公布 —— 按题目所属领域权重加权分配;题数 15~20 题浮动(常见 17 题),每题分值每次考试都不同,约 4~8 分/题(复杂题如集群升级/etcd 还原偏 8 分,简单题如 top 排序偏 4 分)
评分粒度以集群最终状态为准,基本"全对才给分" —— 一题多个子要求漏一个可能整题 0 分(命名空间/标签/名字写错 = 0 分)
出分考后几小时~24h;成绩单只给总分 + 各领域得分条形图,不显示单题对错
证书有效期2 年,到期需重考续证
附赠权益1 次免费重考(首次未过可用)+ killer.sh 模拟器 2 次会话(每次 36 小时窗口,可反复重置)

C2题目 1:Kubernetes 集群升级 ★已精讲

这正是集群架构领域的核心考点。考试会要求你将现有集群(如 1.31.0)的主节点升级到指定新版本(如 1.31.1)。

⚠️ 核心原则:控制平面优先,逐个升级。绝对不能先升级工作节点,必须遵循 控制平面 → 工作节点(逐个) 的顺序。考试通常只要求升级主节点。

升级流程总览(10 步)

①切上下文 ─▶ ②排水master ─▶ ③SSH+提权 ─▶ ④解锁版本包 ─▶ ⑤装指定版本包
                                                              │
⑩验证版本 ◀─ ⑨解除排水 ◀─ ⑧重启kubelet ◀─ ⑦重新锁定包 ◀─ ⑥升级控制平面

每步详细命令与说明(考试必练)

# ────────── 1. 切换集群上下文 ──────────
# 考试环境有多个集群,必须先切换到题目要求的集群(如 xk8s)
kubectl config use-context xk8s

# ────────── 2. 排水主节点 ──────────
# 将节点标记为不可调度,并驱逐其上的 Pod(除 DaemonSet 管理的 Pod 外)
kubectl drain master --ignore-daemonsets

# ────────── 3. 登录主节点并提权 ──────────
# 使用题目提供的 SSH 命令登录,并切换到 root 权限
ssh master
sudo -i

# ────────── 4. 解锁版本包 ──────────
# Ubuntu 系统使用 apt-mark 来管理包版本
apt-mark unhold kubeadm kubelet kubectl

# ────────── 5. 更新软件源并安装指定版本 ──────────
# 确保安装与目标版本匹配的包(版本号必须精确到 -1.1 这种完整后缀)
apt-get update
apt-get install kubeadm=1.31.1-1.1 kubelet=1.31.1-1.1 kubectl=1.31.1-1.1

# ────────── 6. 升级控制平面组件(★核心步骤)──────────
# --etcd-upgrade=false 表示不升级 etcd
kubeadm upgrade apply v1.31.1 --etcd-upgrade=false

# ────────── 7. 重新锁定版本包 ──────────
# 防止后续意外升级
apt-mark hold kubeadm kubelet kubectl

# ────────── 8. 重启 kubelet 服务 ──────────
# 使新的 kubelet 配置生效
systemctl daemon-reload
systemctl restart kubelet

# ────────── 9. 退出主节点并解除排水 ──────────
# 返回到你的考试终端,解除节点的不可调度状态
exit
kubectl uncordon master

# ────────── 10. 最终验证 ──────────
# 检查节点状态,确认版本已更新且节点 Ready
kubectl get nodes
# NAME     STATUS   ROLES           AGE   VERSION
# master   Ready    control-plane   10d   v1.31.1   ← 版本已更新 + Ready 即完成
⚠️ 注意:考试环境可能使用不同的包管理器(如 yum)或 Kubernetes 发行版,但核心逻辑和顺序不变 —— 切上下文 → drain → 升级 kubeadm/kubelet/kubectl 三件套 → kubeadm upgrade apply → uncordon → 验证。务必在模拟环境中反复练习。
💡 两个高频丢分点:① apt-get install 忘写精确版本号后缀(=1.31.1-1.1)装成最新版,直接污染集群;② 升级完忘了 kubectl uncordon,节点一直 NotReady/SchedulingDisabled —— 最后 kubectl get nodes 看一眼 STATUS 列再交卷。

C2B题目 2:RBAC —— 权限绑定(RoleBinding)★已精讲

集群架构领域(25%)高频题,几乎必考。先记住一张关系图:

谁(SA cicd-token)──套上──▶ 绑定(RoleBinding)──写着──▶ 权限(ClusterRole deployment-clusterrole)

权限模板(Role/ClusterRole)  = 能对哪些资源做什么动作
绑定(RoleBinding/ClusterRoleBinding) = 把权限"发给"谁、在哪生效 ← ★作用域在这里定!

考题(中文卷题面为主,英文卷对照保留)

【中文卷】创建一个名为 deployment-clusterrole 的 ClusterRole,仅允许对 deployments、statefulsets 和 daemonsets 三种资源执行 create、update、delete 和 watch 操作。在已存在的命名空间 app-team1 中创建一个名为 cicd-token 的 ServiceAccount。将新建的 ClusterRole 绑定给新建的 ServiceAccount,权限仅在命名空间 app-team1 内生效。
【英文卷】Create a new ClusterRole named deployment-clusterrole, which only allows to create, update, delete and watch the resources deployments, statefulsets and daemonsets. Create a new ServiceAccount named cicd-token in the existing namespace app-team1. Bind the new ClusterRole to the new ServiceAccount limited to the namespace app-team1.

💡 中文卷注意:资源名/动词/命名空间名(deployments、create、app-team1 等)保持英文原词不翻译 —— 它们就是要敲的命令参数,照抄即可;"已存在的(existing)"= 环境预置,直接用勿重建;"仅在 xxx 内生效(limited to the namespace)"= 用 RoleBinding。中英文关键词都认一遍,双保险。

模拟环境准备(★仅 kind 造题用)

kubectl create ns app-team1    # kind 模拟环境里 ns 不存在,先造出来
kubectl get ns app-team1       # 真实考试:"existing namespace" = 集群里已建好,直接用,★勿重复创建!

解法一:纯命令行三连(最快,推荐 —— 每条 = 官方文档模板改参,本地 PS 实测)

# ────────── ① 权限模板:4 个动词 × 3 种资源 ──────────
# 文档模板(RBAC 页"命令行工具"小节,create clusterrole 第 1 条示例):
#   kubectl create clusterrole pod-reader --verb=get,list,watch --resource=pods
# 改 3 处:pod-reader→deployment-clusterrole | get,list,watch→题面 4 动词 | pods→题面 3 资源
PS C:\cka> kubectl create clusterrole deployment-clusterrole --verb=create --verb=update --verb=delete --verb=watch --resource=deployments,statefulsets,daemonsets
clusterrole.rbac.authorization.k8s.io/deployment-clusterrole created
# (--verb 重复写与逗号合并 --verb=create,update,delete,watch 完全等价,抄哪种都对;★认准 clusterrole!)
# (★本题不加 --resource-name:题面限定的是资源"类型"不是具体实例名;加了反而拦掉 create,验证必挂)

# ────────── ② 身份:在指定 ns 建 SA(命令很短,直接手敲)──────────
PS C:\cka> kubectl -n app-team1 create serviceaccount cicd-token
serviceaccount/cicd-token created

# ────────── ③ 绑定(★RoleBinding!引用 ClusterRole 用 --clusterrole=)──────────
# 在哪找:与①同一个页面(RBAC 页“命令行工具”小节),页内 Ctrl+F 搜 create rolebinding
#   → 认准小节标题 kubectl create rolebinding(不带 cluster-),抄第 2 条示例(带 --serviceaccount= 的):
#     kubectl create rolebinding myapp-view-binding --clusterrole=view --serviceaccount=acme:myapp --namespace=acme
# 改 4 处:myapp-view-binding→cicd-token-rb(绑定名自起)| view→deployment-clusterrole
#         acme:myapp→app-team1:cicd-token(冒号=SA所在ns:SA名)| acme→app-team1
PS C:\cka> kubectl -n app-team1 create rolebinding cicd-token-rb --clusterrole=deployment-clusterrole --serviceaccount=app-team1:cicd-token
rolebinding.rbac.authorization.k8s.io/cicd-token-rb created
⚠️ 实测翻车点:输出 created ≠ 对象建对。① 抄文档认准 create clusterrole 小节 —— 抄成 create role 语法照样合法、照样输出 created,但建出来的是 default ns 里的 Role,题目要的 ClusterRole 根本没诞生(评分 0 分)。秒判输出前缀:clusterrole.rbac.authorization.k8s.io/… created 才算建对,role.rbac… created = 建错(前缀=对象类型,★按↑翻历史重跑时先盯它);自查两连:kubectl get clusterrole deployment-clusterrole 能列出 = 建对;kubectl get role deployment-clusterrole -n default 能列出 = 建错,删掉重跑 cluster 版。② --verb 少打 b 报 unknown flag: --ver(客户端拼写错,集群啥也没发生,改对直接重跑)。③ 报 AlreadyExists = 同名对象已在,先跑下方"恢复现场"。④ 文档里带 --resource-name/subresource/non-resource-url/aggregation-rule 的示例本题全不抄:题面限定的是资源"类型"(deployments),不是具体实例名 —— 加 resourceNames 反而会拦掉 create 动作。

解法二:--dry-run 生成 YAML 再 apply(通用套路)

kubectl create clusterrole deployment-clusterrole --verb=create,update,delete,watch \
  --resource=deployments,statefulsets,daemonsets --dry-run=client -o yaml > cr.yaml
kubectl apply -f cr.yaml
# SA、RoleBinding 同理 —— 记不住参数时:先 -h 看帮助,再 --dry-run=client -o yaml 看生成的 YAML
⚠️ 送命题:RoleBinding 还是 ClusterRoleBinding?题目出现 "limited to the namespace xxx" → 必须 RoleBinding(权限只在绑定所在的 ns 生效);只有要求全集群生效才用 ClusterRoleBinding。RoleBinding 引用 ClusterRole 完全合法(把大模板裁剪到本 ns 用),所以参数是 --clusterrole=。用错绑定类型 = 整题 0 分。

验证三连(评分系统干的事,提前人肉做)

# 扮演这个 SA 自问三句:给过的?没给的?范围对不对?
kubectl auth can-i create deployments -n app-team1 --as=system:serviceaccount:app-team1:cicd-token   # 期望 yes
kubectl auth can-i list pods         -n app-team1 --as=system:serviceaccount:app-team1:cicd-token   # 期望 no
kubectl auth can-i create deployments -n default  --as=system:serviceaccount:app-team1:cicd-token   # 期望 no

恢复现场(反复刷题用)

kubectl -n app-team1 delete rolebinding cicd-token-rb
kubectl -n app-team1 delete sa cicd-token
kubectl delete clusterrole deployment-clusterrole
kubectl delete clusterrolebinding cicd-token-rb   # ★集群级,漏删它 = SA 重建后"全集群生效"幽灵复活(can-i@default 变 yes)
# ── 通杀兜底(★清掉所有绑到 cicd-token 的授权,不管绑定叫什么名字/藏在哪个 ns)──
kubectl get clusterrolebinding -o json | ConvertFrom-Json | ForEach-Object { $_.items } | Where-Object { $_.subjects.name -contains 'cicd-token' } | ForEach-Object { kubectl delete clusterrolebinding $_.metadata.name }
kubectl get rolebinding -A -o json | ConvertFrom-Json | ForEach-Object { $_.items } | Where-Object { $_.subjects.name -contains 'cicd-token' } | ForEach-Object { kubectl -n $_.metadata.namespace delete rolebinding $_.metadata.name }
# ── 防残留自查:列出所有绑到 cicd-token 的绑定(应无输出)──
kubectl get clusterrolebinding,rolebinding -A -o wide | findstr cicd-token
💡 考试要全程手敲吗?不用 —— 终端内可复制粘贴,从内嵌官方文档复制 YAML/示例粘进终端也允许(官方鼓励,长 YAML 别手敲);禁止的只是从考试机外部带内容进来。策略:常用命令练成肌肉记忆手敲,长 YAML 从 kubernetes.io 复制后改名改字段。本解法已在 kind v1.31 集群实测通过(yes / no / no 三连验证)。

C2D题目 3:NetworkPolicy —— 网络隔离"先全封,再放行" ★已精讲

服务与网络领域(20%)经典题。前两题 RBAC 管"谁能调 API",这题管"谁能连流量"——思路大反转:RBAC 是给权限,NetworkPolicy 是先全封、再放行。本站 模拟考场第 12 题即此题(题面 / 验证三连 / 一键审计 / 恢复现场全套)。

被管控 Pod(backend,app=backend)一旦被 NetworkPolicy 选中:
  入方向 ──▶ 默认全拒(★没有规则 = 拒绝,不是放行!)
  放行规则(ingress.from)──▶ 同 ns 且 app=frontend ──▶ 仅 TCP 80
  出方向 ──▶ policyTypes 不写 Egress 就不管

考题(中文卷题面为主,英文卷对照保留)

【中文卷】在已存在的命名空间 secure 中,运行着 Deployment backend(镜像 nginx:1.25,标签 app=backend,容器端口 80)和 Service backend。创建一个名为 allow-frontend-only 的 NetworkPolicy,满足:① 只允许同一命名空间内标签为 app=frontend 的 Pod 访问 backend 的 TCP 80 端口;② 除此以外,拒绝所有其他入方向流量(包括来自其他命名空间的);③ 不限制出方向流量。
【英文卷】Create a NetworkPolicy named allow-frontend-only in the existing namespace secure. A Deployment backend(label app=backend)and a Service backend are running there. The policy must allow ingress traffic only from Pods in the same namespace with label app=frontend to the backend Pods on TCP port 80; all other ingress traffic must be denied; egress traffic is not affected.

模拟环境准备(★仅 kind 造题用 —— 本题有一个"CNI 前置":★本机集群已装 Calico,第 0 步自查通过即零成本直接做)

# ── 第 0 步:CNI 自查(★本机集群建群时就装了 Calico —— calico-node DaemonSet 一直在跑)──
kubectl -n kube-system get ds | findstr calico        # 有 calico-node = 支持 NetworkPolicy,下面"重装段"整个跳过,直接出题五条
# ── (仅当上面无输出才需要:kind 默认 kindnet 不支持 NP —— 重装集群 + Calico,只做一次)──
kind delete cluster --name cka
@'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
networking:
  disableDefaultCNI: true        # 禁用 kindnet,podSubnet 对齐 Calico 默认地址池
  podSubnet: 192.168.0.0/16
'@ | kind create cluster --name cka --config=-

apiVersion: networking.k8s.io/v1

  name: allow-frontend-only
  namespace: secure
spec:
  podSelector:                    # ① 管谁:被选中的 Pod 立刻"默认全封"

    - protocol: TCP               # ④ 只放这个端口(漏写 ports = 全端口放行)

C2C题目 6:Deployment 滚动更新与回滚 ★已精讲

工作负载与调度领域(15%)经典题 —— 改镜像 → 看滚完 → 按修订号回滚,一条命令链走完。本站 模拟考场第 2 题即此题(题面 / 验证三连 / 一键审计 / 恢复现场全套),做题去考场,做完回这对照原理。

改镜像(set image)─▶ 滚动出Pod(新RS)─▶ 历史自动记 revision

💡 原理一句话:每次 set image 都会生成一个新 ReplicaSet,旧 RS 保留(副本缩到 0)= revision 历史;undo 不是删除也不是切换,而是把目标 RS 的模板重新应用成新 revision(修订号只增不减)—— 若该模板与某个旧 RS 完全一致(回滚必然如此),控制器会直接复用那个 RS 并把它的 revision 注解改成新号:所以实测 history 显示 1/3/4/5(rev2 被顶替成 5,"消失"是正常现象、不是历史丢了),当前修订号是 5 而不是 2。完整考试化练习(含 6 项一键审计)请进 模拟考场第 2 题。

C2F题目 8:节点维护 —— cordon / drain / uncordon ★已精讲

集群架构领域经典题,也是日常运维的真实动作:cordon = 拉警戒线(只拒新客),drain = 清场(优雅驱逐),uncordon = 解除 —— 一条链三步,考试常考前两步并要求"保持不可调度"。本站 模拟考场第 4 题即此题(题面 / 验证三连 / 一键审计 / 恢复现场全套),做题去考场,做完回这对照原理。

cordon ─▶ 节点 SchedulingDisabled(新 Pod 不来,老 Pod 不动)
   │
   ▼
drain ──▶ 自动 cordon + Eviction API 优雅驱逐 ──▶ 节点清空 → 可安全下线维护
   │           ├─ Deployment 等(受控制器管)→ 在其他节点重建,服务不中断
   │           └─ 裸 Pod(无控制器)→ 驱逐后不复存在(所以默认拒绝,要 --force)
   ▼
uncordon ─▶ 恢复调度(★维护完必做,忘了后面题全调不上)

考题(与考场页第 4 题同源)

节点 cka-worker 需要下线维护:① 将其设为不可调度;② 驱逐其上所有 Pod(允许删除 emptyDir 数据、忽略 DaemonSet;节点上有不受控制器管理的裸 Pod,需 --force 显式确认);③ 完成后保持不可调度状态。

模拟环境准备(★kind 造题 —— 造一个"钉在 cka-worker 上的裸 Pod"给 drain 驱逐;真实考试环境自带,直接从"解法"开始)

kubectl create ns drain-test
$y = @"
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: drain-test
spec:
  nodeName: cka-worker          # ★直接钉死节点,绕过调度器,保证一定在 worker 上
  containers:
  - name: web
    image: nginx:1.25
"@
$y | kubectl apply -f -
Start-Sleep 15
kubectl -n drain-test get pod web -o wide      # 在 cka-worker 上 Running = 出题完成
💡 为什么用 nodeName:kubectl run 不能指定节点、调度器又随机;写死 nodeName: cka-worker 让 Pod 跳过调度直接落在目标节点 —— 题目要 drain 谁,就先往谁身上放东西。

解法(答案):三条命令(本地 PS 实测通过)

kubectl cordon cka-worker
kubectl drain cka-worker --ignore-daemonsets --delete-emptydir-data --force
kubectl get nodes        # 期望:cka-worker = Ready,SchedulingDisabled
💡 三个 flag 的含义(记不住不用背 —— 先敲短的,报错会告诉你加哪个):--ignore-daemonsets = DaemonSet 的 Pod(kube-proxy/CNI)每节点一份、驱逐了会在原地重建,跳过它们;--delete-emptydir-data = 用 emptyDir 的 Pod 一删数据就没,显式授权"可丢";--force = 裸 Pod(无控制器)驱逐后不会在别处复活,drain 默认拒绝,显式授权"可删"。考试开卷:kubectl drain --help 或官方文档 "Safely Drain a Node" 页都有。
⚠️ 实测翻车点:① drain 不带 --ignore-daemonsets 直接报错拒绝(必带,kind/kubeadm 集群都有 DaemonSet);② 漏 --delete-emptydir-data → 报 cannot delete Pods with local storage(kube-system 里就有用 emptyDir 的);③ 节点上有裸 Pod 却漏 --force → 报 cannot delete Pods not managed by ...,drain 半途中止;④ 题目要求"保持不可调度",做完手贱 uncordon 了 —— 审计直接挂;⑤ 反过来:进下一题 / 恢复现场时忘了 uncordon,后面所有 Pod 都调不上 worker(排 Pending 先看 kubectl get nodes 有没有 SchedulingDisabled);⑥ drain 是优雅驱逐(Eviction API),不是 delete —— 别图快直接 delete pod 绕过,考试看的是动作是否标准;⑦ cordon 只影响新 Pod,已在跑的完全不动 —— 别以为 cordon 完节点上就空了。

验证三连(评分系统干的事,提前人肉做)

kubectl get nodes                                    # 期望:cka-worker 的 STATUS=Ready,SchedulingDisabled
kubectl get pods -A --field-selector spec.nodeName=cka-worker   # 期望:只剩 DaemonSet 的 Pod(kube-proxy/kindnet 等)
kubectl -n drain-test get pod web                    # 期望:NotFound(裸 Pod 驱逐后不复存在)
# 进阶:带 OWNER 列,一眼分清谁管的(DaemonSet 会跳过 / ReplicaSet 别处重建 /  是裸 Pod);drain 后 OWNER 应清一色 DaemonSet
kubectl get pods -A --field-selector spec.nodeName=cka-worker -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].kind'

恢复现场(反复刷题用 —— ★第一条 uncordon 必跑)

kubectl uncordon cka-worker                       # ★恢复可调度(忘了它,后面所有题的 Pod 都调不上 worker!)
kubectl delete ns drain-test
# ── 白纸自查 ──
kubectl get nodes                                # 三个都 Ready、无 SchedulingDisabled = 干净
kubectl get ns drain-test                        # NotFound = 干净
💡 原理一句话:cordon 改的是节点 spec.unschedulable(调度器跳过它);drain 先自动 cordon,再对每个 Pod 调 Eviction API(遵守 graceful period、尊重 PDB)—— 受控制器管的 Pod 在别处重建、裸 Pod 一去不返,所以 drain 对"删了回不来"的东西一律要你显式授权。完整考试化练习(含 7 项一键审计)进 模拟考场第 4 题。
