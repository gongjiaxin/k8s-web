03排障三件套(describe / logs / events)

① describe —— 资源的"体检报告",重点看 Events

kubectl describe pod harbor-database-0 -n harbor | tail -9
  database-data:
    Type:        PersistentVolumeClaim (...)
    ClaimName:   harbor-database      # 挂的哪个 PVC
QoS Class:       BestEffort
Tolerations:     node.kubernetes.io/not-ready:NoExecute op=Exists for 300s
Events:          <none>              # 健康时无事件;出问题时这里全是线索
# 排障时直接看尾部 Events,典型报错:
#   FailedScheduling ... persistentvolumeclaim "xxx" not found → PVC 名错(本集群真实踩过)
#   FailedMount ... unable to attach volume → 卷挂载失败
#   BackOff ... container has run out of memory → OOM 被杀

② logs —— 看进程输出,日志永远在 Pod 不在 Service

kubectl logs -f harbor-database-0 -n harbor          # -f 实时滚动
kubectl logs -f deploy/harbor-core -n harbor        # deploy 简写(自动挑副本,免抄哈希)
kubectl logs <pod> -n harbor --previous              # ★ 看上一次崩溃的日志(CrashLoop 必杀)
kubectl logs <pod> -n harbor -c registry --tail=100  # 多容器 Pod 指定容器+只看百行

③ events —— 集群级"事件流水",按时间排序

kubectl get events -n harbor --sort-by=.lastTimestamp | tail -5
# 健康集群输出为空(正常);出问题时 Warning 事件会密集出现,
# 与 describe 的 Events 是同源数据,但可跨资源、可排序、可持续 watch:
kubectl get events -A -w --sort-by=.lastTimestamp   # -w 挂着实时盯全集群事件
⚠️ 90% 启动故障 = 三件套两条命令:Pending → describe 看 Events;CrashLoop → logs --previous;连锁崩溃永远先修最上游。完整实战认证见 Pending 23h 排障实录。

04进容器与调试(exec / 端口转发)

# 在容器里执行命令(deploy 简写 + 指定容器,实测输出):
kubectl exec -n harbor deploy/harbor-portal -c portal -- echo 'hello from container'
hello from container

# 交互式进容器排障(相当于 docker exec -it)
kubectl exec -it -n harbor deploy/harbor-core -- sh

# 本地端口转发:不暴露服务,从办公网直接访问集群内 ClusterIP
kubectl port-forward svc/harbor-portal -n harbor 8080:80
# Forwarding from 127.0.0.1:8080 -> 8080 → 浏览器开 http://localhost:8080 即可调试
# Ctrl+C 结束;--address=0.0.0.0 可让局域网访问

# 容器与本地互拷文件
kubectl cp -n harbor harbor-database-0:/tmp/a.log ./a.log   # 容器 → 本机
kubectl cp ./b.txt -n harbor harbor-database-0:/tmp/        # 本机 → 容器
💡 临时调试容器:目标镜像里没有 curl/sh 时,用 kubectl run tmp --rm -it --image=nicolaka/netshoot -n harbor -- bash 起一个万能工具箱 Pod,查 DNS/网络连通性后退出即自动删除。

05变更操作(apply / scale / rollout)—— 动手改集群

# 声明式应用清单(最常用,可重复执行,幂等)
kubectl apply -f k8s/harbor-ingress.yaml     # 单文件
kubectl apply -f k8s/                        # 整个目录一键部署
kubectl apply -f https://xxx/xxx.yaml        # 直接吃远程 URL

# 删除(支持同款简写;删 ns 会连带删里面所有资源,慎用!)
kubectl delete -f k8s/harbor-ingress.yaml
kubectl delete pod harbor-redis-0 -n harbor          # 删 Pod(sts/deploy 会自动重建)
kubectl delete deploy/harbor-portal -n harbor        # 删 deploy(副本全下线)

# 伸缩副本数
kubectl scale deploy/harbor-portal -n harbor --replicas=3
# deployment.apps/harbor-portal scaled → get pods 立刻多出 1 个

# 滚动发布三连
kubectl rollout status deploy/harbor-portal -n harbor
# deployment "harbor-portal" successfully rolled out   ← 实测输出
kubectl rollout restart deploy/harbor-portal -n harbor  # 滚动重启(改了 CM/密钥后常用)
kubectl rollout undo deploy/harbor-portal -n harbor     # 一键回滚上个版本

# 临时在线编辑(改完保存立即生效,适合调探针/环境变量)
kubectl edit deploy/harbor-core -n harbor

# 打标签(svc 靠标签找 Pod,标签错=流量断)
kubectl label pods harbor-portal-xxx -n harbor env=test --overwrite
💡 顺序习惯:改配置 → apply → rollout status 盯到 successfully → get pods 复核;不对就 rollout undo,三步之内必能回到健康态。

07输出格式与实用技巧 —— 速查表

写法作用示例
-o wide多列(IP/NODE 等),排网络必备get pods -o wide
-o yaml完整对象定义,学习/备份/复刻get deploy harbor-core -o yaml
-o jsonpath精准抠字段进脚本get -o jsonpath='{.items[*].metadata.name}'
-w挂住持续 watch 变化get pods -n harbor -w
--show-labels显示标签(svc↔Pod 靠它关联)get pods --show-labels
-l k=v按标签过滤get pods -l app=harbor
--sort-by按字段排序get events --sort-by=.lastTimestamp
-A所有命名空间get pods -A
--all-containers多容器 Pod 全看logs -l app=harbor --all-containers
💡 高频组合拳:kubectl get pods -A | grep -v Running(揪出所有异常 Pod)、kubectl get deploy,sts,svc,pvc -n harbor(一次看四类资源)、watch kubectl get pods -n harbor(全屏盯发布过程)。
