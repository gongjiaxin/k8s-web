报错分类:先分清三个层面

报错层面定性
Error 1040: Too many connections to MySQL RouterRouter 进程自身的连接额度(默认 512,本案已调 3000/副本)主故障
dial tcp 10.107.24.34:3306: connect: connection refusedTCP 层:Service 的某个 endpoint 上没有进程在监听(容器已死)主故障的第二面
Error 1049 Unknown database 'heartbeat' / Error 1286 Unknown storage engine 'TOKUDB'exporter 采集器配置噪音无害,顺手关闭(见 08 节)
⚠️ 关键分辨点:同样是 1040,带 "to MySQL Router" 是 Router 自己拒绝的;不带(只有 "Too many connections")才是后端 MySQL 的 max_connections 打满。一字之差,排查方向完全不同 —— 本案主库从头到尾没有打满。

破案起点:时间轴上的轮询规律

把报错按时间排开,发现 "1 次 refused + 3 次 1040"以 2 分钟为周期循环 —— 恰好等于 4 个 endpoint × 30 秒抓取间隔:

02:01:32  1040      ← endpoint B:满
02:02:02  refused   ← endpoint A:容器已死,但还在 Service 里
02:02:32  1040      ← endpoint C:满
02:03:02  1040      ← endpoint D:满
02:03:32  1040      ← 轮回 endpoint B:满
02:04:02  refused   ← 轮回 endpoint A:仍死
        (周期 = 4 × 30s = 2 分钟,严丝合缝)

由此直接推断拓扑真相:3 个活着的 Router 都已顶到各自上限,第 4 个 Router 容器已经死了 —— 后面所有排查都在验证这两点。

04排查 —— 七步破案

第 1 步:读日志找规律(零成本,信息量最大)

不急着敲命令,先把报错按时间轴排开 —— 得到 "1 refused + 3×1040"的 2 分钟循环(见 02 节),直接锁定"3 满 1 死"的拓扑假设。规律比单条报错值钱。

第 2 步:describe Router Pod,拿到底牌

$ kubectl -n fke-db describe pod fke-mysql-hmsserver-prod-router-6c5f8cfb7-4jsz6
Environment:
  MYSQL_ROUTER_BOOTSTRAP_EXTRA_OPTIONS:  --conf-set-option=DEFAULT.max_total_connections=3000
                                          --conf-set-option=DEFAULT.connect_timeout=10
                                          --conf-set-option=DEFAULT.client_connect_timeout=30
                                          --conf-set-option=routing:bootstrap_rw.connection_sharing=1
                                          --conf-set-option=routing:bootstrap_ro.connection_sharing=1
Liveness:       http-get https://:http/api/20190715/swagger.json delay=0s timeout=1s period=10s #failure=3

三个结论:① 限额已是 3000,不是默认 512 → 排除"调小限额没调";② BestEffort + 1s liveness → 容器有被误杀的风险;③ readiness 只 cat 一个 emptyDir 文件 → 容器死了探针照样通过,refused 之谜有了解释框架。

第 4 步:processlist 三连 —— 决定性反差

实例 Pod 的容器名是 mysql(不是 mysqld),root 密码在 InnoDBCluster 的 spec.secretName 指向的 secret 里(key 为 rootUser / rootPassword):

RU=$(kubectl -n fke-db get secret fke-mysql-hmsserver-prod-cluster-secret -o jsonpath='{.data.rootUser}' | base64 -d)
PW=$(kubectl -n fke-db get secret fke-mysql-hmsserver-prod-cluster-secret -o jsonpath='{.data.rootPassword}' | base64 -d)
for i in 0 1 2; do
  kubectl -n fke-db exec fke-mysql-hmsserver-prod-$i -c mysql -- mysql -u"$RU" -p"$PW" -e "
    SELECT MEMBER_ROLE FROM performance_schema.replication_group_members WHERE MEMBER_ID=@@server_uuid;
    SELECT user, db, command, COUNT(*) cnt, MAX(time) max_idle_s
      FROM information_schema.processlist GROUP BY user, db, command ORDER BY cnt DESC;
    SHOW GLOBAL STATUS LIKE 'Threads_connected';"
done
# 主库(-1,PRIMARY)关键输出:
#   my_role: PRIMARY
#   hms    dmpcloud  Sleep  4    4      ← 真实业务连接只有个位数!
#   hms    hmscloud  Sleep  1    0
#   Threads_connected: 9 / 3 / 3(三台)

Router 上堆着 ~9000 条连接,后端真实业务连接只有 ~6 条 —— 巨大反差说明那些连接不是活跃业务,而是空转的占位者。注意:RW 路由是 first-available,连接全在主库上,processlist 必须看主库才有意义(用 MEMBER_ROLE 先认角色)。

第 6 步:/proc/net/tcp 抓现行 —— 零依赖的取证神器

重启后 Router 计数从零开始,正好观察"谁在连"。6446 的十六进制是 192E,对端地址在第 3 列(IP 字节倒序)。一条 awk 聚合出每个客户端 IP 的连接数:

for p in 4jsz6 h65pj t7mjp ztmlx; do
  echo "== $p =="
  kubectl -n fke-db exec fke-mysql-hmsserver-prod-router-6c5f8cfb7-$p -- \
    sh -c "awk '\$4==\"01\" && \$2 ~ /:192E\$/ {ip=substr(\$3,1,8); cnt[substr(ip,7,2) \".\" substr(ip,5,2) \".\" substr(ip,3,2) \".\" substr(ip,1,2)]++} END {for (i in cnt) printf \"%4d %s\n\", cnt[i], i}' /proc/net/tcp | sort -rn"
done

#    4 10.244.190.235     ← release-server-ltzzs

05根因 —— 9000 条僵尸连接 + 探针"永真"缺陷

完整因果链

~01:0x  复制/负载事件(GR applier 卡 6736s 线索,起点未完全闭环)
  └→ 主库变慢,应用查询超时 → 无退避地疯狂重连,旧连接被弃成"僵尸"
       └→ 3 个 Router 各自的 3000 连接额度被僵尸占满
            └→ 新连接一律 Error 1040 "Too many connections to MySQL Router"
                 └→ 第 4 个 Router 容器死亡(BestEffort + 1s liveness,疑似被饿杀)
                      └→ readiness 只 cat emptyDir 里的文件 → "永真" → 死 endpoint 仍挂 Service
                           └→ kube-proxy 每 4 次轮询命中它 1 次 → connection refused
                                └→ mysqld_exporter 每 30s 报警(报警人 = 受害最深的客户端)

为什么主库全程无感?

三重保险叠加:① 僵尸连接全部空闲,connection_sharing=1 让空闲客户端不占后端连接(客户端连接 ~130 条时,主库 Threads_connected 只有 ~9,压缩比 15:1);② 主库 max_connections=3000 余量充足;③ 错误日志零 "Too many connections" 佐证。死的只是 Router 的"接待能力",数据库本体毫发无损。

为什么一次重启就能解决?

僵尸连接的客户端进程早已消失或放弃 —— Router 断开后它们无人重建;而合法应用(~17 个 Pod 的连接池)会在几分钟内自动回填 ~130 条正常连接。所以重启 Router = 把额度账本撕了重记,留下来的全是真用户。

为什么 refused 每 2 分钟才出现一次?

4 个 endpoint 轮询 + 30 秒抓取间隔 = 2 分钟才轮到那个死 Pod 一次。这是探针缺陷的指纹:readiness 探针 cat /tmp/mysqlrouter/mysqlrouter.conf 检查的文件放在 emptyDir 卷里,容器崩溃重启后文件依然存在,探针永远成功 → Pod 永远 Ready → 死 endpoint 永远在 Service 里接流量。

⚠️ 遗留线索(未完全闭环,记入待办):① SECONDARY 实例的 GR applier 线程卡了 6736 秒(≈1 小时 52 分,正好指向 01:0x 的事故起点),需查 replication_group_member_stats 与 innodb_trx 确认是否有大事务/DDL;② 主库曾出现 sha256_password is deprecated 告警,某客户端仍在用旧认证插件;③ 凭据曾在终端输出过,建议轮换。

# 04 节第 6 步那条 awk 一把梭:按客户端 IP 聚合 4 个 Router 的 ESTABLISHED 连接

巡检 C:主库侧(连接归属 + 余量)

# 04 节第 4 步的 for 循环 + 这两条:
SELECT SUBSTRING_INDEX(host,':',1) AS src_ip, COUNT(*) AS conns
  FROM information_schema.processlist GROUP BY src_ip ORDER BY conns DESC;
SHOW GLOBAL STATUS LIKE 'Aborted%';   -- Aborted_clients 持续走高 = 有客户端非正常消失(僵尸前兆)

巡检 D:复制健康(本案遗留项,建议纳入常规)

SELECT MEMBER_HOST, MEMBER_ROLE,
       COUNT_TRANSACTIONS_IN_QUEUE                AS cert_queue,
       COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE AS applier_queue
  FROM performance_schema.replication_group_member_stats s
  JOIN performance_schema.replication_group_members m ON m.MEMBER_ID = s.MEMBER_ID;
-- cert_queue / applier_queue 为 0 或个位数 = 健康;持续非零 = applier 卡住(01:0x 事件的形态)

SELECT trx_started, trx_weight, trx_rows_locked, trx_rows_modified, trx_state
  FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 5;
-- 长事务(trx_started 很久之前)= 大事务/DDL 卡复制的高危信号

4 Router 总连接稳定在 ~130(±)健康稳态无需动作

快速冲高(分钟级)+ 应用侧超时报错重连风暴进行中先稳主库(查巡检 D),再给应用加退避;必要时滚动重启 Router 止血
单副本 activeConnections → 3000即将 1040提前重启该副本,同时按上面两条找堆积来源
周期性 connection refused有 endpoint 容器死亡但探针没摘get endpoints 对照 get pods,重启死副本;根治见 08 节第 1 条

08加固清单 + 报错速查表

防复发(按优先级)

  1. Router 加 resources(requests/limits):摆脱 BestEffort,根治"高负载 CPU 被饿 → 1s liveness 误杀 → 死容器仍 Ready 接流量"的连锁;同时可放宽 liveness timeout(1s → 3~5s)
  2. 应用重试加指数退避 + 上限,连接池 maxLifetime < wait_timeout:根治"主库一慢就重连风暴",这是本次僵尸的制造机
  3. Router :8443 /metrics 纳入 Prometheus(凭据用 rest-monitor secret),告警阈值 activeConnections > 1500 —— 距打满 3000 还有数小时缓冲,不用再靠 exporter 的 1040 报错发现事故
  4. 限额对齐:4 副本 × 3000 = 12000,而 first-available 把 RW 流量全灌主库(主库 max_connections=3000)。建议单副本降到 ~700(总量 ≤ 主库上限),或上调主库 max_connections 并核算内存
  5. exporter 消噪:加 --no-collector.heartbeat --no-collector.engine_tokudb_status,日志里只剩真故障
  6. 轮换凭据:rest-monitor / router 两个 secret 的内容曾在排障终端输出过
  7. 01:0x 复制事件立案:applier 卡 6736s 的起点(大事务/DDL?)用巡检 D 的 SQL 回溯,它是本次风暴的第一块多米诺
