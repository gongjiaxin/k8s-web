01什么是 Ingress

Ingress 是 Kubernetes 中负责 七层(HTTP/HTTPS)流量入口 的资源对象,提供:

  • 基于 域名(host) 和 路径(path) 的路由转发
  • TLS 终止(集群入口统一卸载 HTTPS)
  • 重写、限流、CORS、超时等增强能力(通过各 Controller 的注解实现)
⚠️ 最常见的坑:Ingress 资源本身只是"一份规则声明",不处理任何流量。必须部署一个 Ingress Controller(如 ingress-nginx)watch 这些规则并生成实际的反向代理配置,否则创建 Ingress 毫无效果。
ServiceIngress
工作层级四层(TCP/UDP)七层(HTTP/HTTPS)
路由依据端口域名 / 路径 / Header / 权重
典型用途集群内服务发现与负载均衡统一外部入口、TLS 卸载、灰度

Ingress vs 传统独立 NGINX

💡 先说透本质:ingress-nginx 的 Controller 底层就是 nginx,它做的事是把 Ingress 规则"翻译"成 nginx.conf 并热加载。所以两者不是二选一的竞争关系,而是动态 vs 静态、云原生 vs 传统的分工。
维度传统 NGINX(独立部署)K8S Ingress(ingress-nginx)
配置方式手改 nginx.conf + reload,改错易滚挂kubectl apply 声明式,Controller 校验后自动热加载
服务发现手写 upstream IP,后端扩容要人跟改自动 watch Service/Endpoints,Pod 扩缩自动跟进
负载均衡upstream 轮询/权重,目标固定跨 Pod 自动分发,支持会话保持等策略
发布能力Lua/脚本拼灰度,门槛高注解开箱即用:金丝雀、重写、限流、CORS
多团队协作一台机器一份 conf,大家挤着改每个应用一个 Ingress 资源,命名空间隔离、可审计
适用后端任意 IP:端口(虚机/物理机/容器都行)只路由 K8S 集群内的 Service

为什么在 Ingress 前面再挡一层 NGINX(本环境实际架构)

┌──→ 虚机/物理机上的老应用(静态站点、传统服务) 用户 ──→ 外层NGINX ──┤ (主从+VIP) └──→ K8S NodePort :31588 ──→ ingress-nginx ──→ Pod
  • 边缘与集群解耦:对外入口永远是外层的 80/443;集群迁移、重建、换 Controller、NodePort 变更,外层只改一行 upstream,域名和用户无感。
  • 混合流量调度:同一入口下,老系统(虚机 nginx 站点)与新 K8S 服务共存 —— 按 server_name/location 分流,一部分转虚机、一部分转集群,迁移期两套并行(本环境 hello1/hello2 老站点与 k8s-web 新站点正是这样过渡)。
  • 统一证书管理:TLS 证书集中在外层续期替换,不必把证书分发进集群 Secret,一处换、处处生效。
  • 安全加固收口:IP 白名单、限流、防扫描、WAF 挂点统一放外层;集群内 Controller 保持配置简单,减少攻击面。
  • 集群外高可用:外层主从 + VIP 漂移,入口存活不依赖 K8S 本身 —— 即使整个集群故障,外层仍能返回维护页/兜底页,而不是用户直接超时。
  • 日志审计统一:边缘访问日志格式统一、集中,排障永远"由外向内"(见第 2 节分层排障命令)。
⚠️ 代价要心里有数:多一跳转发(毫秒级延迟)、多一层组件要运维、Host 头必须透传(丢了 Ingress 404)。小规模纯 K8S 场景直连 NodePort/LB 也够用;存在"老应用混合、需稳定对外、证书集中管理"需求时,这层才真正物有所值 —— 本环境三条全占,所以这么搭。

📄 配置① 外层 NGINX:/etc/nginx/conf.d/k8s.ergesanbaishou.com.conf

⚠️ 血泪教训:此文件名必须以 .conf 结尾 —— nginx 只 include conf.d/*.conf,无后缀文件静默不加载,nginx -t 也不报错,页面表现为"默认欢迎页"。改完必须 nginx -t && nginx -s reload。(文件头部注释是旧站点遗留,可顺手更新)
# =========================================================
# hello1.qingfeng.dev → K8s Ingress → nginx-hello(qingfeng空间)
# 外层nginx:80 → ingress-nginx NodePort:31080 → svc:8080 → pod:80
# (↑ 旧站点遗留注释;实际生效: k8s.ergesanbaishou.com → 31588)
# =========================================================
upstream k8s_ergesanbaishou {
    server 10.18.170.34:31588;     # ★ ingress-nginx 的 NodePort(HTTP 入口)
    keepalive 32;
}

server {
    listen 80;
    server_name k8s.ergesanbaishou.com;

    access_log /var/log/nginx/hello1.access.log;
    error_log  /var/log/nginx/hello1.error.log;

    location / {
        proxy_pass http://k8s_ergesanbaishou;

        # ★★★ 灵魂行:透传 Host,Ingress 全靠它分流,丢了必 404 ★★★
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket 支持(可选,有需要就留着)
        proxy_http_version 1.1;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        "upgrade";

        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}

📄 配置② 业务负载:k8s-web.yaml(Deployment + Service)

💡 两条验证路径:NodePort 32001 可绕过整条 ingress 链路直连 Pod(排障时先测它:curl http://10.18.170.34:32001/);hostPath 指向 Pod 所在节点 的 /data/git/web,改页面即时生效。
apiVersion: apps/v1
kind: Deployment
metadata:
  name: k8s-web
  namespace: ergesanbaishou
  labels:
    app: k8s-web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: k8s-web
  template:
    metadata:
      labels:
        app: k8s-web
    spec:
      # (可选)固定到单一节点,只需维护一份文件:
      # kubectl label node <节点名> k8s-web=true
      # nodeSelector:
      #   k8s-web: "true"
      containers:
      - name: nginx
        image: nginx:alpine
        ports:
        - containerPort: 80
        # 用 tcpSocket 而非 httpGet:目录为空时 httpGet / 返回 403 会卡住 NotReady
        readinessProbe:
          tcpSocket: {port: 80}
          initialDelaySeconds: 3
        livenessProbe:
          tcpSocket: {port: 80}
          initialDelaySeconds: 10
        resources:
          requests: {cpu: 50m, memory: 64Mi}
          limits:   {cpu: 200m, memory: 128Mi}
        volumeMounts:
        - name: web
          mountPath: /usr/share/nginx/html    # 容器内 nginx 站点根目录 → 节点 /data/git/web
      volumes:
      - name: web
        hostPath:
          path: /data/git/web                 # ★ 节点上的真实目录
          type: DirectoryOrCreate             # 目录不存在时 kubelet 自动创建(空目录访问 / 会 403)
---
apiVersion: v1
kind: Service
metadata:
  name: k8s-web
  namespace: ergesanbaishou
  labels:
    app: k8s-web
spec:
  type: NodePort
  selector:
    app: k8s-web
  ports:
  - name: http
    port: 8080                  # ★ 线上 Service 统一开放 8080(集群内/Ingress 访问用它)
    targetPort: 80              # 容器内 nginx 仍监听 80,这个不用动
    nodePort: 32001    # 全集群唯一;直连测试用(curl 节点:32001)
# 域名/Ingress 访问方式见 ingress.yaml(入口端口 31588)

📄 配置③ 路由规则 + 集群入口:ingress.yaml(Ingress + controller Service)

💡 核心概念:Ingress 规则本身没有入口端口参数!31588 是 ingress-nginx-controller 的 NodePort,由本文件第二段的 Service 固定;Ingress 只声明"host + path → svc:port"。
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: k8s-web
  namespace: ergesanbaishou
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "false"   # 暂无证书,先不强制跳 https
spec:
  ingressClassName: nginx          # 对应 ingress-nginx;其他 controller 名要改
  rules:
  - host: k8s.ergesanbaishou.com   # ★ 指定域名,只有 Host 为它的请求才命中本规则
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: k8s-web         # k8s-web.yaml 里部署的 Service
            port:
              number: 8080        # ← 对应 svc k8s-web 的 port(8080),不是 targetPort(80)

  # ---- 第二个站点(备用,当前注释未生效)----
  # 上线步骤:部署对应 Deployment+Service → 取消注释 → apply → 外层 nginx 加 server 块
  # - host: test2.ergesanbaishou.com
  #   http:
  #     paths:
  #     - path: /
  #       pathType: Prefix
  #       backend:
  #         service:
  #           name: test2-svc
  #           port:
  #             number: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-controller
  namespace: ingress-nginx
  labels:
    app.kubernetes.io/name: ingress-nginx
    app.kubernetes.io/component: controller
spec:
  type: NodePort
  selector:
    app.kubernetes.io/name: ingress-nginx
    app.kubernetes.io/component: controller
  ports:
  - name: http
    port: 80
    targetPort: 80
    protocol: TCP
    nodePort: 31588               # ★★★ 集群 HTTP 入口,外层 nginx proxy_pass 指向它
  - name: https
    port: 443
    targetPort: 443
    protocol: TCP
    # https 的 nodePort 不指定 → 保留/自动分配(30255);上证书要固定时照抄 http 段

🔥 踩坑实录(本环境搭建过程真实案例)

症状根因解法
页面显示 nginx 默认欢迎页conf 文件名没有 .conf 后缀 → include conf.d/*.conf 静默不加载,nginx -t 也不报错改名加后缀 + nginx -t && nginx -s reload
默认欢迎页(另一种)hosts 把域名解析到了错误机器(如 K8S 节点,上面另有一个 nginx)hosts 必须指向外层 NGINX 机器的 IP
直连 31588 返回 404裸 curl IP:31588 没带 Host 头 → Ingress 按 host 路由匹配不上(正常行为,非故障)curl -H "Host: k8s.ergesanbaishou.com" http://10.18.170.34:31588/
外层转发放大后 404外层 nginx 没写 proxy_set_header Host $host → 域名没透传给 controller补上灵魂行并 reload(见配置①)
apply 报 namespaces "ingress-nginx" not found先 apply 了 Ingress,但 controller 还没安装先装配置④,再 apply 配置③
apply 报 nodePort 32001 冲突旧 test1 的 Service 还占着 32001kubectl delete svc test1-ergesanbaishou -n ergesanbaishou

04流量链路

客户端 ──→ LB / NodePort ──→ Ingress Controller(Pod, nginx) │ 读取 Ingress 规则 ▼ ┌─ host: api.example.com + /foo ──→ foo-svc ──→ Pods ├─ host: api.example.com + /bar ──→ bar-svc ──→ Pods └─ 其他 ──→ defaultBackend(404)

Controller 本身也是一个 Pod,需要先通过 NodePort / LoadBalancer / hostNetwork 之一把自身暴露到集群外。

06第一个 Ingress:域名 + 路径路由

保存为 ingress-demo.yaml 后 kubectl apply -f ingress-demo.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
  annotations:
    # 把 /foo/xxx 转发到后端时重写为 /xxx
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx            # 由哪个 Controller 处理
  rules:
    - host: api.example.com          # 省略 host 则匹配所有域名
      http:
        paths:
          - path: /foo(/|$)(.*)      # 正则捕获组配合 $2 使用
            pathType: ImplementationSpecific
            backend:
              service:
                name: foo-svc
                port:
                  number: 80
          - path: /bar
            pathType: Prefix
            backend:
              service:
                name: bar-svc
                port:
                  number: 8080
  defaultBackend:                    # 兜底后端(都不匹配时返回)
    service:
      name: default-svc
      port:
        number: 80

本地没有域名解析时,用 curl -H "Host: api.example.com" http://<INGRESS_IP>/foo/xx 模拟测试。
