02第①层:公司 DNS —— 域名怎么进来

公司统一域名后缀 *.ergesanbaishou.com(如私仓 docker.ergesanbaishou.com)。域名并不直接指向 K8S 节点,而是指向外层 NGINX 的 VIP —— 这样 K8S 集群怎么扩缩、节点 IP 怎么变,域名永远不用改。

# 在办公网任一机器上验证解析
nslookup xxx.ergesanbaishou.com        # 返回的 IP 应是 NGINX 的 VIP,而不是节点 IP
# 入口类 *.ergesanbaishou.com 域名通常都指向同一个 VIP —— 这就是"统一入口"的特征

03第②层:外层 NGINX 主备 + VIP —— 集群外的高可用入口

两台 NGINX(一主一备)通过 keepalived 共享一个 VIP(虚拟 IP):平时 VIP 在 Master 上,Master 挂了 VIP 自动漂到 Backup,客户端无感知不断流。所有进入 K8S 的 HTTP(S) 流量先到这里,再 proxy_pass 转发到 K8S 节点的入口端口。

组件职责关键点
NGINX-Master承接 VIP,反代到 K8Skeepalived 心跳互探;VIP 漂移秒级完成
NGINX-Backup热备,Master 挂则接管 VIP
VIP对外的"稳定 IP"域名解析到它,后端随便换
💡 2026-10 实测补充:这台 NGINX 是全公司统一入口,不只代理 K8S —— nginx -T 里还有大量直连物理机后端(192.168.3.x、10.18.x 各端口)的 proxy_pass,K8S 只是其后端之一;进 K8S 的流量统一走"节点 IP + NodePort"(30080/30538 两扇门),绝不会写 ClusterIP。完整实测见 04 节。
💡 与测试环境同构:测试集群的外层 NGINX 主从 + VIP 链路(k8s.ergesanbaishou.com → VIP → NodePort 31588)就是线上这套的缩小版,完整配置见 K8S 证书管理 与 Ingress 文档 02 节。★ 灵魂行永远是 proxy_set_header Host $host; —— 不透传域名,后端路由必 404。

04第③层:fke 集群与入口网关(双网关并存 · 2026-10 实测)

🚪 先搞懂:为什么说"双网关"?—— 大楼有两扇门

入口网关 = 集群的大门保安。外部流量不能随便打进某个 Pod(IP 会变、数量多、不安全),必须先过一扇"大门",由保安按域名 + 路径决定转给哪个 Service —— 这就是网关干的全部事。

线上这栋"楼"装了两套独立的门禁系统,是并联关系(不是串联 —— 门A 不会把流量再转发给门B):

                     外层 NGINX 主备(VIP)
                    ┌─────┴─────┐
          普通业务域名的流量      网格类平台的流量(如 kubeflow/knative)
                    │            │
                    ▼            ▼
        ┌──────────────────┐  ┌──────────────────────────┐
        │ 🚪 门A: nginx-ingress │  │ 🚪 门B: istio-ingressgateway   │
        │ ns: kube-infra        │  │ ns: istio-system              │
        │ NodePort 30080/30443  │  │ NodePort 30538/30539          │
        │ 按 Ingress 规则路由    │  │ 按 Gateway/VirtualService 路由 │
        └──────────┬───────────┘  └──────────┬─────────────────────┘
                   ▼                         ▼
              Service → Pod             Service → Pod
        (两扇门都通向楼内,只是"门禁系统"不同)
  • 门A(nginx-ingress):传统主流方案,与测试集群同款同原理;业务 Web 服务的流量大多走这。
  • 门B(Istio 网关):服务网格体系自带的大门;kubeflow、knative 这类平台组件按 Istio 方式暴露,流量走这。
  • 谁决定走哪扇门?外层 NGINX 的转发规则(upstream 指到 30080 还是 30538)—— 具体配置待确认(见 07 节)。
# 想知道哪些服务走哪扇门?(在 fke 上跑)
sudo kubectl get ingress -A     # 门A 的"访客名单":每条规则 = 一个域名/路径 → 后端服务
sudo kubectl get gateway -A     # 门B 的名单(Istio Gateway 资源)

🏨 网关按 ns 分吗?—— 不分!一扇大门服务所有 ns

实测全集群只有一个 istio-ingressgateway(Service 10.100.189.102,装在 istio-system)—— 它是集群级大门,所有 ns 共用。网关不按 ns 分,"路由规则"才按 ns 分:各业务 ns 提交自己的"门牌登记"(Istio 里叫 Gateway/VirtualService),网关汇总所有 ns 的登记形成一张总路由表 —— 大门一个,门牌无数。

              istio-ingressgateway(istio-system,全集群 1 个)
                            ▲
        ┌───────────┬───────┴──────┬───────────┐
        │ 登记       │ 登记         │ 登记       │   ← 各 ns 提交路由规则
   kubeflow ns    app ns       knative ns  ...
  (VirtualService)          (Gateway/VS)
        │           │              │
        ▼           ▼              ▼
     本 ns 的 Service → Pod

门A 是同一个模式:一个 controller(kube-infra)监听全集群所有 ns 的 Ingress 规则 —— 测试集群也一样(Ingress 写在 web ns,controller 装在 ingress-nginx ns)。例外:超大集群可能部署多个 ingressgateway(内/外网流量分开),但本集群 get svc -A 只有一个 → 共用模式。

# 验证:谁在门B 登记过?
sudo kubectl get gateway,virtualservice -A      # 各 ns 提交的"门牌"清单
sudo kubectl get svc -A | grep ingressgateway   # 全集群只有一个网关 Service → 共用

🔌 域名到底怎么找到 Pod?—— 域名选规则,规则选 Service,Service 选 Pod

两扇门殊途同归:域名匹配的是"路由规则",规则选中的是 Service;Pod 不是被域名直接选中的,而是 Service 用 label selector 挑出来的(Endpoints 的本质 = "这个 Service 名下有哪些 Pod"的名单)。

门A(nginx-ingress):
  请求(host+path) → Ingress 规则 → backend.service.name = 某 Service ──┐
                                                                     │
门B(Istio):                                                          ├─→ Service(label selector)
  请求(host) → Gateway(定义监听) + VirtualService(host+path 匹配)     │      → Endpoints → Pod
              → destination.host = 某 Service ───────────────────────┘
                              (两种门到这一步完全一样)
# 查门A 每条规则指向哪个 svc(SVC 列就是答案):
sudo kubectl get ingress -A -o custom-columns='NS:.metadata.namespace,HOST:.spec.rules[*].host,SVC:.spec.rules[*].http.paths[*].backend.service.name'

# 查门B 每条规则指向哪个 svc(DEST 列就是答案):
sudo kubectl get virtualservice -A -o custom-columns='NS:.metadata.namespace,HOSTS:.spec.hosts,DEST:.spec.http[*].route[*].destination.host'

# 再往下一层:Service 选中了哪些 Pod
sudo kubectl get ep <svc名> -n <ns>     # Endpoints 里的 IP 列表 = 后端 Pod 真实 IP
💡 澄清易混点:istio-ingressgateway 自己就是一个 Service(NodePort 30538,门本身);它"找哪个 svc"不是它自己决定的,而是看各 ns 提交的 VirtualService 规则里的 destination.host。Istio 特例:VS 也能直连 Pod 或 ServiceEntry(外部服务),但主流用法仍是走 Service。

🔍 怎么确认外层 NGINX 走哪扇门?(在 nginx-master 上查)

⚠️ 实测踩坑:在外层 NGINX 配置里 grep 网关的 ClusterIP(10.100.189.102)永远搜不到 —— 不是没走它,而是 ClusterIP 只有集群内可达!外层 NGINX 在集群外,upstream 只能写节点 IP + NodePort(与 MySQL 文档 M5"宿主机 ping 不通 Pod IP"同一知识点)。
IP 类型示例谁能访问
ClusterIP10.100.189.102仅集群内(Pod/节点上) —— 外层 nginx 写了也连不通
NodePort节点IP:30080任何能连节点 IP 的机器 ← 外层 NGINX 只能用这个
# ① 终极命令:dump 全部生效配置再筛(比 grep conf.d 全,include 的其他路径一网打尽)
sudo nginx -T 2>/dev/null | grep -E "proxy_pass|server " | grep -v "#"

# ② 按端口号搜(不是搜 IP!)
grep -rn "30080\|30443" /etc/nginx/     # 命中 → 有流量走门A(nginx-ingress)
grep -rn "30538\|30539" /etc/nginx/     # 命中 → 有流量走门B(istio 网关)

# ③ 都搜不到的三个可能:a.配置不在 conf.d(用 nginx -T 确认 include 范围)
#   b.nginx-backup 那台也有配置(两台都看)  c.istio 流量不经这台 nginx(内网直连 NodePort 或另有入口)

# ④ 集群侧反查交叉验证:看门B 登记了哪些域名,再拿域名回 nginx 配置里 grep
sudo kubectl get virtualservice -A -o custom-columns='NS:.metadata.namespace,HOSTS:.spec.hosts'

实证落地:9 条 VS 9 个路径,各管一段 —— /jupyter/ 进笔记本、/katib/ 进调参、/pipeline 进流水线…其中 centraldashboard 匹配 /(根路径)= 兜底门户:没命中具体组件前缀的请求落到门户首页(Istio 按最长前缀优先匹配,/ 最宽所以天然垫底)。

⚠️ 易混点:不是"不同域名→不同路径",而是"同一个域名的不同路径→不同组件"。域名和路径是同一个 URL 的两半,分流是接力棒式的:

浏览器地址栏:  https://kubeflow-new.ergesanbaishou.com/jupyter/notebook1
               └──────────── 域名(host) ───────────┘└─ 路径(path)─┘

三棒接力(每棒只看自己那半):
① 公司 DNS     看"域名" → 解析到外层 NGINX 的 VIP
② 外层 NGINX   看"域名" → kubeflow-new.* → 30538 进门B(域名使命到此结束)
③ 门B 的 VS    看"路径" → /jupyter/ 命中 jupyter 那条 → jupyter-web-app-service

门B 里所有流量的域名都一样,变的只是路径:
  kubeflow-new.…/           → / (兜底)   → 门户首页
  kubeflow-new.…/jupyter/   → /jupyter/  → 笔记本
  kubeflow-new.…/katib/     → /katib/    → 调参
  kubeflow-new.…/pipeline   → /pipeline  → 流水线

"有相同的"解惑:HOSTS 列全 [*] 是真的全相同 —— 第③棒不看域名,通配一切;MATCH 列 9 个路径互不相同(都以 / 开头只是路径的标准写法),单独的 / 是最宽的兜底。比喻:域名决定去哪栋楼,路径决定进楼后去几号窗口。

💡 顺手的坑:缩写 vs 会触发 Warning —— 它还能匹配 volumesnapshots(存储快照)资源;kubectl 已自动选了高优先级的 virtualservices,确认意图即可,怕歧义可写全称 virtualservices。
  • 读表两点:① 门B 服务 3 个 ns(kubeflow ×9 + auth ×1 + oauth2-proxy ×1)—— 实锤"一扇大门服务所有 ns";② DEST 全是 <Service名>.<ns>.svc.cluster.local 标准长格式(与 MySQL 文档 M5 的 DNS 公式同一套)。
  • 认证链浮出水面:oauth2-proxy(统一认证代理)+ dex(OIDC 身份源)也在门B —— 外部请求先过认证链再到 kubeflow 各组件,这就是 oauth2-proxy / auth 两个 ns 的真实角色。
  • kubeflow 全家桶 UI 全在门B:centraldashboard(门户)/jupyter-web-app(笔记本)/katib(调参)/kserve(模型服务)/ml-pipeline(流水线)/profiles(多用户)/tensorboards/volumes —— 9 条 VS 正好对应 kubeflow 平台的 9 个 Web 组件。
