01先对比:Argo Workflows 和 ArgoCD / Argo 家族的区别

动手装之前先把"Argo"这个词理清楚——它是一整个家族,平时说的"装 Argo"十有八九指的是装错了东西:

项目一句话定位操作对象典型使用者
Argo CDGitOps 持续部署:把 Git 仓库里的 YAML 同步到集群应用(Application / 部署清单)发布 / 运维
Argo Workflows ← 本页K8S 原生工作流引擎:把任务编排成一串容器跑批Workflow / CronWorkflow数据处理 / 定时任务
Argo Rollouts渐进式发布(金丝雀 / 蓝绿)Rollout 资源发布策略
Argo Events事件驱动(触发 Workflows 等)EventSource / Sensor自动化联动
一句话记忆:ArgoCD 管"代码 → 集群"的部署,Argo Workflows 管"在集群里跑任务"。线上 fke 集群两套都装了、互不依赖;new-k8s 单点这次只装 Workflows。

更完整的对照(含两套系统在 fke 上的部署形态、端口、CRD 对比)见 线上 Argo Workflows 部署档案 §01 与 ArgoCD 档案。

02线上架构参照(fke)与 new-k8s 单点安装定位

new-k8s 这次安装对齐线上 fke 的版本(v3.7.9)和组件形态,但部署方式完全不同:

维度线上 fke(参照)new-k8s(本次目标)
版本v3.7.9(workflow-controller + argo-server)同 v3.7.9,与线上保持一致,便于经验迁移
安装方式Helm 在线装,release 名 fke,资源前缀 fke-argo-workflows-开发机下好 Chart 包 + 镜像 → ctr 导入 → Helm 本地 tgz 离线装,release 名 argo
拓扑controller / server 各 1 副本(实际就是单点形态)单点:默认即非 HA、无外部 DB、无 MinIO,chart 默认值就是单点,无需任何额外配置
命名空间argo(工作流也在 argo ns 跑)同样装到 argo ns,提交流程与线上一致
artifacts未验证(待查 controller configmap)首装不配置(chart 不依赖 MinIO/DB);后续要产物存储再加
网络内网 registry docker.fftaicorp.com/kube-public/完全离线:镜像以 ctr images import 落到节点本机
为什么"单点"反而省事:Argo Workflows 官方 chart 默认安装的就是非 HA 版(controller、server 各 1 副本,SQLite 级元数据、不接外部数据库)——线上 fke 的形态恰好就是它。所以 new-k8s 不需要写任何 HA / DB values,默认值即目标形态。

03开发机下载清单(★ Chart + 镜像 + CLI)

先说结论 —— 版本怎么选(已核实,别下错): 官方 chart 从来没有打包过 v3.7.5~v3.7.9:3.7 线最后一个 chart 是 argo-workflows-0.45.28(内置 appVersion v3.7.4),之后直接跳到 1.0.0(v4.0.2)。所以不要 helm pull 最新版(那是给 v4 + 新增 crdinstaller 镜像用的)。正确做法:chart 用 0.45.28,镜像钉死 v3.7.9,通过 images.tag 一个参数全局生效。

04传输与导入(scp + ctr images import)

把 4 个文件传到 new-k8s 节点,再用 containerd 导入(-n k8s.io 命名空间必须带上,k8s 只认这个空间里的镜像):

# 开发机 → new-k8s 节点(单点就传一台;多节点要么每台导,要么推公司 harbor)
scp wf-controller-v3.7.9.tar argocli-v3.7.9.tar busybox-1.36.tar \
    argo-workflows-0.45.28.tgz argo-linux-amd64.gz  用户@new-k8s节点:/opt/argo-install/

# 登录 new-k8s 节点,导入镜像(每个 tar 一次)
cd /opt/argo-install
sudo ctr -n k8s.io images import wf-controller-v3.7.9.tar
sudo ctr -n k8s.io images import argocli-v3.7.9.tar
sudo ctr -n k8s.io images import busybox-1.36.tar

# 验证导入结果(确认 quay.io/argoproj/... 两个镜像在列)
sudo ctr -n k8s.io images list | grep -E 'argoproj|busybox'

# argo CLI 解压安装到 /usr/local/bin
sudo sh -c 'gunzip -c argo-linux-amd64.gz > /usr/local/bin/argo && chmod +x /usr/local/bin/argo'
argo version   # 应显示 argo v3.7.9
✅ CLI 实测(new-k8s-fke-m1,2026-11):argo version 实际输出 argo: v3.7.9 / GitTag: v3.7.9 / BuildDate: 2026-01-28T14:53:27Z / Platform: linux/amd64 —— 与线上 fke 的 v3.7.9 同一构建,版本对齐目标达成。CLI 目前只装在 fke-m1,其余节点如需就地操作重跑同一条命令即可。
镜像名不用改:导入后镜像名保持 quay.io/argoproj/... 原样,配合 values 里 pullPolicy: IfNotPresent(见 §05),kubelet 发现本机已有就直接用,不会去外网拉。
✅ 实测记录:5 节点批量分发与导入(2026-11)——含一个已抓到的坑

new-k8s 实际拓扑:5 节点(10.18.51.121~125),文件统一放 /tmp/argoworkflows/。批量姿势(scp 循环分发 + ssh 循环导入):

for i in `seq 121 125`; do echo $i; ssh root@10.18.51.$i "cd /tmp/argoworkflows/ && ctr -n k8s.io images import wf-controller-v3.7.9.tar"; done
for i in `seq 121 125`; do echo $i; ssh root@10.18.51.$i "cd /tmp/argoworkflows/ && ctr -n k8s.io images import argocli-v3.7.9.tar"; done

导入成功后 ctr -n k8s.io images list 实测:workflow-controller:v3.7.9 43.4 MiB、argocli:v3.7.9 68.8 MiB、busybox:1.36 2.1 MiB(与开发机 docker save 的 tar 大小对得上)。

⚠️ 已抓到的坑:循环跑完后在 new-k8s-fke-m1 手动复核,发现 argocli:v3.7.9 缺失(workflow-controller、busybox 都在)——history 里第 1991 条循环用了中文弯引号实际没生效,靠 1992 重跑才救回来。教训:循环 import ≠ 每台都成功,必须逐台复核。缺哪台补哪台(文件在 /tmp/argoworkflows/ 就地补导):ctr -n k8s.io images import /tmp/argoworkflows/argocli-v3.7.9.tar

逐台复核(补导后实测 2026-11):121~125 五台全部输出 4 = 3 个目标镜像 + 1 个节点预存的 docker.1ms.run/library/busybox:1.36.1(grep 子串误命中:busybox:1.36.1 包含 busybox:1.36 字样)。五台一致即全就绪 ✅。只数目标三件的精确版(应得 3):

for i in `seq 121 125`; do echo "== 10.18.51.$i =="; ssh root@10.18.51.$i "ctr -n k8s.io images list | grep -E 'argoproj/(argocli|workflow-controller):v3.7.9|busybox:1.36' | wc -l"; done

# 精确版:锚定完整镜像名,排除 1ms.run 预存 tag 的干扰
ctr -n k8s.io images list | grep -cE 'quay\.io/argoproj/(argocli|workflow-controller):v3\.7\.9|docker\.io/library/busybox:1\.36 '

05Helm 单点安装(values 全文 + 两个必踩坑)

① values-offline.yaml(单点最小配置,全文)

# ===== Argo Workflows 离线单点安装 values(new-k8s)=====
# 单点 = chart 默认形态:非 HA、无外部 DB、无 MinIO,以下只写必须覆盖的四处
images:
  tag: v3.7.9               # ★坑1:不写则取 chart 内置 appVersion v3.7.4!必须钉死 v3.7.9 对齐线上
  pullPolicy: IfNotPresent  # ★坑2:chart 默认 Always,离线环境会去 quay.io 拉镜像 → ImagePullBackOff 卡死

# 资源名固定为 argo-*(不加则是 argo-argo-workflows-*,又臭又长)
fullnameOverride: argo

# ★坑3:UI 认证模式(chart 与官方清单的隐蔽差异)。官方 quickstart 显式带 --auth-mode=server,
# helm chart 默认不传 → argo-server 落到上游默认 client 模式 → 浏览器没 token,
# UI 调接口必报 code 16 "token not valid"。改 server 模式后浏览器免 token 直接用;
# 代价 = "能打开页面 = 全权操作",网关 nginx 必须加 basic auth!
server:
  authModes:
    - server
  # ★坑4:对外 NodePort 必须写进 values!kubectl patch 改的 NodePort 是带外改动,
  # helm upgrade 会按 chart 默认(ClusterIP、无 nodePort)把它冲掉 → 网关 nginx 直接 502(2026-11 实测)
  serviceType: NodePort
  serviceNodePort: 30274

# 以下全部走默认,即单点目标形态:
#   crds.install: true        → 首次 install 自动装 workflows.argoproj.io 全套 CRD
#   controller.replicas: 1 / server.replicas: 1 → 各 1 副本
#   不配 persistence/postgres → 不需要数据库
#   不配 artifactRepository   → 暂不启用 artifacts(后续要存储再加,可选 MinIO)

② 安装命令

# 建 ns(chart README 也建议部署在 argo ns,工作流默认也在这个 ns 跑)
sudo kubectl create namespace argo

# 用本地 tgz 安装,release 名 argo
sudo helm install argo ./argo-workflows-0.45.28.tgz -n argo -f values-offline.yaml

# 观察启动
sudo kubectl get pods -n argo -w
两个必踩坑(都是查官方 values.yaml 原文核实的): ① images.tag 默认空 → 回落 chart 内置的 v3.7.4,装出来版本就和线上 3.7.9 对不上; ② images.pullPolicy 默认 Always → 离线集群每次调度都尝试连 quay.io,Pod 永远 ImagePullBackOff。这两个不写,装完必翻车。
实测坑③(2026-11,fke-m1 真实发生):终端粘贴多行 heredoc 被截断。 整块粘贴 cat > xx.yaml <<'EOF' ... EOF 时命令与回显交错,heredoc 没闭合 → values-offline.yaml 根本没生成,后续 helm install 也没执行,而 kubectl create ns 却成功了——结果就是 ns 空空如也不知道为啥。防坑三招:① 多行配置用 printf 单行版替代 heredoc(printf 'images:\n tag: v3.7.9\n pullPolicy: IfNotPresent\nfullnameOverride: argo\n' > values-offline.yaml);② 写完必 cat 验文件;③ 粘贴长命令块时一条一条来。另注:new-k8s 的 root 直接 kubectl/helm 即可(fke 的 kubeconfig 是 root-only 必须 sudo,环境差异勿混淆)。
✅ 实测记录(2026-11,fke-m1 操作;new-k8s 的 root 直接跑 kubectl/helm,无需 sudo):
kubectl create namespace argo → Active;helm install argo ./argo-workflows-0.45.28.tgz -n argo -f values-offline.yaml → deployed;两组件 1/1 Running(同落 new-k8s-fke-n3 节点,五节点都导了镜像所以调度无忧);kubectl -n argo get svc 只有 argo-server(ClusterIP 10.107.6.73,2746/TCP)。

装完的资源名(配了 fullnameOverride: argo):argo-workflow-controller + argo-server 各 1 副本,Service 为 argo-server(:2746,UI/API)。注意:chart 默认不创建 controller 的 metrics Service(metricsConfig.enabled=false),线上 fke 若有 metrics svc 属于额外开启,两边对照时别误判。UI 临时访问:kubectl -n argo port-forward svc/argo-server 2746:2746,对外域名反代见 §08。

进阶:仿线上 collecte-batch 的多步流水线(单点复刻版)

线上真实业务的运转方式:外部系统(Jenkins/GitLab/数据平台)提交带批次参数的 Workflow → controller 把每个 step 拆成独立 Pod 调度 → 步骤间靠 artifact 仓库传文件 / 参数传小数据 → 完成后归档 + TTL 清理(无 cronwf,不是定时驱动)。下面用参数传递串一条五步流水线(collect → convert → annotate×3 并行 → qc → downstream),复刻线上形态:

cat > mini-pipeline.yaml <<'EOF'
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: mini-collecte-
spec:
  entrypoint: pipeline
  arguments:
    parameters:
    - name: batch-id
      value: batch-001
  templates:
  - name: pipeline
    steps:
    - - name: collect
        template: collect
    - - name: convert
        template: convert
        arguments:
          parameters:
          - name: raw
            value: "{{steps.collect.outputs.parameters.raw-count}}"
    - - name: annotate
        template: annotate
        withSequence:
          count: "3"
        arguments:
          parameters:
          - name: valid
            value: "{{steps.convert.outputs.parameters.valid-count}}"
    - - name: qc
        template: qc
        arguments:
          parameters:
          - name: annotated
            value: "{{steps.convert.outputs.parameters.valid-count}}"
    - - name: downstream
        template: downstream
        arguments:
          parameters:
          - name: passed
            value: "{{steps.qc.outputs.parameters.pass-count}}"
  - name: collect
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [collect] batch={{workflow.parameters.batch-id}} fetched 100; echo 100 > /tmp/out"]
    outputs:
      parameters:
      - name: raw-count
        valueFrom:
          path: /tmp/out
  - name: convert
    inputs:
      parameters:
      - name: raw
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [convert] got {{inputs.parameters.raw}} raw, 95 valid; echo 95 > /tmp/out"]
    outputs:
      parameters:
      - name: valid-count
        valueFrom:
          path: /tmp/out
  - name: annotate
    inputs:
      parameters:
      - name: valid
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [annotate] worker on {{inputs.parameters.valid}} records, done"]
  - name: qc
    inputs:
      parameters:
      - name: annotated
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [qc] reviewed, 93 pass; echo 93 > /tmp/out"]
    outputs:
      parameters:
      - name: pass-count
        valueFrom:
          path: /tmp/out
  - name: downstream
    inputs:
      parameters:
      - name: passed
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [downstream] stored {{inputs.parameters.passed}} records, batch {{workflow.parameters.batch-id}} done"]
EOF
argo submit -n argo mini-pipeline.yaml --watch     # 预期 7 个节点全绿,annotate×3 并行
argo logs @latest -n argo | grep '^\['             # 看数据接力:100 → 95 → 93
与线上差距对照:① 线上步骤间传文件靠 artifact 仓库(S3/MinIO + persistence),单点要传真实文件需先架 MinIO 或用 volumeClaimTemplates 挂 PVC(workflow 级 emptyDir 每个 Pod 独立,不共享!);② 线上用 WorkflowTemplate 沉淀流水线定义、提交时只传参数(13node/12node 就是同模板不同参数),单点学习阶段内联即可;③ 坑(2026-11-19 首跑实测):executor 的 init 容器用的是 argoexec 镜像(chart 默认 quay.io/argoproj/argoexec:v3.7.9),与 argocli 是两个东西——离线清单漏了它,首个 Workflow 必卡 Init:ErrImagePull;修复见 §07 报错表新增行。
验收进度(2026-11):关一 ✅ 两组件 1/1 Running(§05 实测);关二、关三(CLI 连通 + 离线 hello-world)待执行——hello-world 的测试 Pod 会随机调度到任意节点,五台镜像都已导入,不用怕。

报错速查

现象原因处理
Workflow Pod 卡 Init:ErrImagePull执行器镜像 argoexec 不在节点上——离线导入清单只有 controller + argocli,而 chart executor 默认 quay.io/argoproj/argoexec:v3.7.9,首个 Workflow 跑到一半才暴露(2026-11-19 mini-pipeline 首跑实测)确认 init 要的名字:kubectl get pod <pod> -n argo -o jsonpath='{range .spec.initContainers[*]}{.image}{\"\\n\"}{end}' → 开发机下载 argoexec(出不了 quay 可用 docker.1ms.run 中转后 docker tag 改回原名)→ 五台节点 sudo ctr -n k8s.io images import → 删掉卡住的 wf 重提
Pod ImagePullBackOffpullPolicy 还是默认 Always,在连 quay.iovalues 改 IfNotPresent 后 helm upgrade;并 ctr -n k8s.io images list 确认镜像真的导进去了
装出来版本是 v3.7.4没写 images.tag,回落 chart 内置 appVersionimages.tag: v3.7.9 钉死后 upgrade
UI 报 {"code":16,"message":"token not valid"}chart 默认不传 --auth-mode,上游默认 client 模式,浏览器没 token(官方清单默认 server 模式所以没这问题)values 加 server.authModes: [server] 后 helm upgrade,浏览器强刷;server 模式=免登录全权限,网关 nginx 务必开 basic auth
helm upgrade 后旧 Pod 显示 Terminating → Error滚动更新正常收尾:新 Pod Ready 后旧 Pod 收 SIGTERM 退出,非零码退出被标 Error,随即对象删除不是故障;确认新 ReplicaSet 的 Pod 1/1 Running 即可,几秒后旧 Pod 自动消失
upgrade 后网关 502 Bad Gateway,域名打不开helm upgrade 按 chart 默认把 kubectl patch 的 NodePort 冲回 ClusterIP,30274 没了kubectl -n argo get svc argo-server 确认;values 声明 serviceType/serviceNodePort 后再 upgrade(详见 §08 告警框)
提交的 Workflow 一直 Pending节点资源不足 / selector 不匹配describe pod 看事件;单点节点注意预留资源
Workflow 卡 Running 不结束经典坑:容器主进程退了但 wait 边车(或被注入的 sidecar)不退出确认 workflow 是否被注入额外 sidecar,必要时加 sidecar.istio.io/inject: "false" 类注解后验证
UI 打不开(localhost:8080)连错端口::8080 是 controller 的 metrics,不是 APIUI/API 走 argo-server:2746,见 线上档案 §03 端口陷阱

08对外访问:NodePort + nginx 域名反代(80→301→443)

照 new-k8s Longhorn 的老套路:svc patch 成命名 NodePort → 网关 nginx(new-k8s-nginx-1)80 转 301、443 反代五节点。目标域名:new-argoworkflows.fftaicorp.com(网关实机证书为 _.fftaicorp.com 泛域名,域名匹配直接绿锁)

① argo-server svc 开 NodePort(命名端口 30274)

kubectl patch svc argo-server -n argo \
  -p '{"spec":{"type":"NodePort","ports":[{"name":"web","port":2746,"targetPort":2746,"nodePort":30274,"protocol":"TCP"}]}}'

kubectl get svc argo-server -n argo    # 2746:30274/TCP 即成功
curl -I http://10.18.51.121:30274/     # 任一节点返回 HTTP 200/302 即通
⚠️ 实测坑(2026-11):NodePort 千万别只靠 kubectl patch!patch 是带外改动,下一次 helm upgrade 会按 chart 默认把它冲回 ClusterIP(30274 消失),网关立刻 502、域名打不开。正确姿势:values 里声明 server.serviceType: NodePort + server.serviceNodePort: 30274,让 helm 自己管。排查口诀:502 先看 kubectl -n argo get svc argo-server 里 30274 还在不在。
✅ 实测(2026-11):patch 一次成功,2746:30274/TCP;首次 curl 偶发 connection refused,1 秒后重试即 200——patch 后 kube-proxy 的 iptables 规则同步有秒级延迟,不是故障。HTTP 200 直出也顺带证实了 --secure=false(argo-server 内部就是纯 HTTP,nginx 可放心写 proxy_pass http://)。

② 先验内部 TLS 模式(决定 nginx upstream 用 http 还是 https)

kubectl get deploy argo-server -n argo -o yaml | grep -- '--secure'
# chart 默认 --secure=false → argo-server 内部走纯 HTTP,nginx 直接 proxy_pass http://
# 若是 --secure=true(自签 HTTPS)→ upstream 改 https:// 并加 proxy_ssl_verify off;

③ 网关 nginx 配置(/etc/nginx/conf.d/new-argoworkflows.fftaicorp.com.conf,已实测部署)

upstream argoworkflows_ui {
    server 10.18.51.121:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.122:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.123:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.124:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.125:30274 max_fails=2 fail_timeout=10s;
}
server {
    listen 80;
    server_name new-argoworkflows.fftaicorp.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl http2;    # 语法坑:nginx < 1.25.1 不认独立的 "http2 on;" 指令(new-k8s-nginx-1 实测报 unknown directive)
    server_name new-argoworkflows.fftaicorp.com;

    ssl_certificate     /etc/nginx/ssl/_.fftaicorp.com.pem;    # 网关实机泛域名证书,域名匹配直接绿锁
    ssl_certificate_key /etc/nginx/ssl/_.fftaicorp.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;

    # 建议开启:argo-server 默认 auth-mode=server,UI 本身不登录,
    # 外层 basic auth 就是唯一门锁(照 Longhorn 惯例)
    #auth_basic "argo workflows";
    #auth_basic_user_file /etc/nginx/htpasswd/argoworkflows;

    location / {
        proxy_pass http://argoworkflows_ui;
        proxy_set_header Host            $host;
        proxy_set_header X-Real-IP       $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_http_version 1.1;                      # 日志流 / WebSocket 必须带
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
        client_max_body_size 0;
    }
}
nginx -t && nginx -s reload
upstream 为什么写全部 5 台(含 121/122 两台 master)而不是只写 worker?NodePort 是 kube-proxy 层的东西:每台节点的 30274 都在监听,流量从任一节点进来,kube-proxy 都会转给 Service 背后的 Pod——实测就是证据:Pod 只在 n3,从 m1(121)的 30274 进,照样 200。master 的污点(NoSchedule)只挡"调度 Pod",不挡"转发流量"。两种写法都合法:写 5 台 = 入口池最大、任一节点维护时入口不断、与 Longhorn 站点配置同构好排查;只写 123/124/125 三台 worker 也完全能跑(master 不承载业务入口、省 master 的 conntrack/带宽、防火墙少开两个口),按团队规范选即可,小集群实际差异微乎其微。

④ DNS 与安全

  • 内网 DNS 加 A 记录:new-argoworkflows.fftaicorp.com → nginx 网关 IP(与 Longhorn 同套路);
  • 浏览器验收:https://new-argoworkflows.fftaicorp.com → Argo Workflows UI,绿锁(网关证书 _.fftaicorp.com 泛域名匹配);
  • 安全红线:30274 只对网关 IP 放行(防火墙堵旁路),别全网段裸奔——fke 上 30010 裸奔 447 天的教训就在档案里。
为什么走 NodePort 直连而不是 ingress-nginx:ingress-nginx(30080/30443)建 Ingress 转发当然也行,但 NodePort 直连与 Longhorn 运维套路一致、链路少一层、排查简单;Argo UI 的 WebSocket 日志流在两层代理里都得带 Upgrade 头,链路越短越不容易踩坑。
