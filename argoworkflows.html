01先分清:Argo Workflows ≠ ArgoCD(对比大表)

两个项目同属 Argo 家族,名字像、Logo 像、版本号都是 v3.x 格式,但是两个完全独立的软件。线上最典型的混淆坑:在集群里 get ns | grep -i argo 只看到 argo 这个 ns(里面是 Argo Workflows),很容易误判"线上只装了一个 Argo" —— 实际上 ArgoCD 藏在 kube-infra,见 线上 ArgoCD 部署档案 01 节的排坑实录。

维度Argo Workflows(本篇 · ns: argo)ArgoCD(ns: kube-infra)
定位任务编排引擎:在 K8S 里跑批处理流水线(DAG / 步骤)GitOps 持续交付:把 Git 里的 YAML/Helm 同步到集群
干的事跑 Job:数据转换、质检、标注、ETL、训练管部署:应用该跑什么版本、漂了自动拉回
触发方式手动提交 / CronWorkflow 定时 / Argo Events 事件Git 仓库一变就自动 diff + sync
核心 CRDWorkflow / CronWorkflow / WorkflowTemplateApplication / ApplicationSet
核心组件workflow-controller + argo-serverargocd-application-controller + argocd-server(+ redis、repo-server、dex)
状态模型任务型:Running / Succeeded / Failed,跑完即结束持续型:Sync Status(Synced/OutOfSync)+ Health Status,持续纠偏
UI 一眼识别左侧菜单 Workflows、Workflow Templates;条目是步骤图、耗时、日志左侧菜单 Applications、Settings;条目是 Git 仓库、Path、Destination
线上版本v3.7.9(controller 与 argocli 同版本)v3.1.4(chart argo-cd-8.3.5,HA)
一句话"帮我在集群里跑一批任务""帮我把集群变成 Git 描述的样子"
💡 冲突吗?不冲突,两个独立项目,组件名(argo-* / argocd-*)、CRD、配置互不相干。本集群就是共存实证:argo ns 管数据流水线,kube-infra 管应用交付。还能联动:ArgoCD 把 WorkflowTemplate 纳入 Git 管理、Argo Events 事件触发 Workflows 跑批。

04生产运行现状(collecte-batch 跑批 + kubeflow 残留)

Workflows 在这个集群不是摆设,是生产主力:2026-11-19 实测时,argo ns 里同时有数十个 step Pod 在滚动执行(每分钟都有新的创建 / 完成),全部来自数据采集批流水线 workflow-collecte-batch-*。

⚠️ 2026-11-19 下午复测更新(时效备注):同日再查状态已变 —— kubectl get wf -A 全集群 0 条活工作流、cronwf -A 为空、argo ns 仅剩 server + controller 两个 Pod(两组件 7d3h 前刚重装/重启)。即 collecte-batch 此刻静默:且无 cronwf 说明它从来不是定时驱动,触发入口在上游系统(Jenkins / GitLab / 数据平台),当前可能是"批次间隙"也可能是重装后停批待恢复。判定方法:UI 归档列表看 argo ns 最新条目的时间戳(几小时内 = 活着间隙中;7 天前 = 随重装停了)、kubectl get wftmpl -n argo 看模板定义是否还在、kubectl logs -n argo deploy/fke-argo-workflows-workflow-controller --tail=100 看近期有无处理痕迹。业务② aurora 构建(fcb-pipeline)同样静默,最近一次执行在 6 天前(见 08 节)。

🏗️ 调度与容器特征

  • 业务 step Pod 调度在 fke-01-runner / fke-03-runner 节点,与 controller/server 所在的控制面节点(fke-n9/n12)分离,职责清晰。
  • step Pod 都是 2/2 容器 —— 主容器 + 1 个伴随容器,疑为 Istio sidecar 注入(argo ns 在 ELK 日志采集范围内,与 mesh 方案吻合),待验证(命令见 07 节)。

🧹 遗留物:kubeflow ns 的僵尸 controller

全集群扫描时发现 kubeflow ns 里还有一个 workflow-controller Deployment:0/0 副本、367 天没动 —— 疑似早期 KubeFlow 集成时的遗留物,副本数为 0 不占运行资源,但会污染 get deploy -A | grep workflow 的结果,待确认无人使用后清理(连带其 Service)。

⚠️ 生产跑批不停,动手红线:① 不要在 argo ns 里随意提交试验 Workflow / 改 WorkflowTemplate;② 不要动 collecte-batch 相关模板与 CronWorkflow;③ 摸清并发限制(parallelism / nodeEvents)之前,不要提交大批量测试;④ 资源名全带 fke-argo-workflows- 前缀,操作前先 get 确认名字。

05版本与巡检命令速查

# ★ 前提:普通用户(fourier)没有 kubeconfig,必须 sudo —— 否则报 localhost:8080 refused
sudo kubectl get deploy,sts,svc,pods -o wide -n argo          # 组件全景

# 版本(资源名带 Helm release 前缀,别直接 get deploy workflow-controller!)
sudo kubectl get deploy -n argo \
  -o custom-columns='NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image'
sudo kubectl get pods -n argo -L app.kubernetes.io/version     # 组件 Pod 版本列

# CRD 级巡检(kubectl 直接操作 Workflow CRD,无需 argo CLI)
sudo kubectl get wf -n argo --no-headers | wc -l               # 存量 Workflow 总数
sudo kubectl get wf -n argo --sort-by=.metadata.creationTimestamp | tail -10
sudo kubectl get cronwf -n argo                                 # 定时流水线清单
sudo kubectl get crd | grep argoproj.io                         # CRD 清单
sudo kubectl get crd workflows.argoproj.io \
  -o jsonpath='{.status.storedVersions}'; echo                  # CRD 存储版本

# 控制器配置(configmap 同样带前缀;executor/artifact/并发全在这)
sudo kubectl get cm -n argo | grep -i workflow                  # 先确认 configmap 真名
sudo kubectl get cm fke-argo-workflows-workflow-controller-configmap -n argo -o yaml

# Helm(同样要 sudo)
sudo helm list -n argo                                          # release / chart 版本
sudo helm get values fke -n argo                                # 当年安装的 values 全量
💡 为什么命令都带 sudo?线上 kubeconfig 在 root 用户下(/root/.kube/config 或 kubeadm 的 admin.conf)。普通用户没有 kubeconfig 时,kubectl/helm 会退化连 localhost:8080,于是看到 refused。若要免 sudo,给 fourier 配一份受控权限的 kubeconfig + ServiceAccount(走 RBAC)更规范。

06argo CLI 安装(版本对齐 v3.7.9)

线上服务器(fke-m1)没装 argo CLI。建议装与服务端一致的 v3.7.9,避免 CLI 与 CRD 版本错位:

# 服务器能出外网:
curl -sLO https://github.com/argoproj/argo-workflows/releases/download/v3.7.9/argo-linux-amd64.gz
gunzip argo-linux-amd64.gz && chmod +x argo-linux-amd64
sudo mv argo-linux-amd64 /usr/local/bin/argo
sudo argo version          # 应输出 arg v3.7.9

# 内网拉不到 GitHub → 直接用私仓里的 CLI 镜像:
sudo docker run --rm docker.fftaicorp.com/kube-public/argocli:v3.7.9 version
💡 CLI 怎么连?argo CLI 默认直连 K8S API 操作 Workflow CRD,不经过 argo-server,所以装完即可 sudo argo list -n argo。只有看 Web UI 才需要 2746 端口:临时调试用 sudo kubectl -n argo port-forward svc/fke-argo-workflows-server 2746:2746,长期入口应走 Ingress(是否存在待确认,见 07 节)。

07注意事项与待确认清单(动手前必读)

#待确认事项验证命令为什么要确认
1controller 配置全貌(executor 类型 / artifact / 并发限制)sudo kubectl get cm fke-argo-workflows-workflow-controller-configmap -n argo -o yaml决定实验边界:能不能提交大批量、产物怎么传
2是否配置了数据库(persistence / archive)argo ns 里未见 DB pod;看 sudo helm get values fke -n argo没开的话 Workflow 历史全存 etcd + CRD,GC 策略不明有 etcd 膨胀风险;开了的话 DB 在哪要摸清
2026-11-19 实测进展:归档确认已开启 —— UI 历史工作流 ARCHIVED=true、kubectl get wf 已 NotFound 但记录仍可查(详见 08 节);DB Pod 不在 argo ns,疑在 fke-db,configmap persistence 段待确认
3artifact 存储(S3 / MinIO / 未配置)configmap 的 artifactRepository 段 + helm values步骤间传文件靠它;没配则只能靠参数/日志传数据
4step Pod 2/2 容器是否 Istio sidecar挑一个 Running 的 step Pod:sudo kubectl get pod 名称 -n argo -o jsonpath='{range .spec.containers[*]}{.name} {.image}{"\n"}{end}'sidecar 必须随主容器正常退出,否则 Workflow 卡 Running 不结束(mesh + workflow 经典坑)
5argo-server 认证模式(sso / client / paranoid)与 Ingresssudo kubectl get deploy fke-argo-workflows-server -n argo -o yaml | grep -iE 'auth|sso|mode'; sudo kubectl get ingress -n argo确认 UI 是否裸奔在集群内、要不要补认证
6kubeflow ns 残留的 0 副本 workflow-controller确认 KubeFlow 集成是否已弃用后:sudo kubectl delete deploy,svc -n kubeflow -l ...(先 get 确认)消除干扰项,避免 grep 误判
7CronWorkflow 清单与调度规律sudo kubectl get cronwf -n argo搞清 collecte-batch 是定时触发还是上游系统提交,避免实验撞车
⚠️ 与 ArgoCD 协作提醒:如果后续想用 ArgoCD 管理 WorkflowTemplate / CronWorkflow(GitOps 化),注意 ArgoCD 在 kube-infra ns、Workflows 在 argo ns,Application 的 destination namespace 要写 argo;同步策略建议手动 sync,防止误删生产跑批模板。

08aurora-build 摸底实录(归档机制 + Argo vs Tekton 双轨评估)

2026-11-19 开着 Argo UI 巡检时,在 aurora-build ns 意外撞见 3 条跑完的构建流水线,顺着挖下去把「归档机制」和「线上 CI 选型动向」两个问题一次摸清。

🔍 UI 里看到的 3 条工作流(aurora-build ns)

工作流进度耗时解读
fcb-pipeline-13node-d6pbp13/136m14sfcb 构建流水线的参数化变体:13node / 12node = 目标节点数参数;PROGRESS 13/13 说明有 13 个步骤节点(疑为并行 fan-out);generateName 随机后缀,典型 CI 提交特征;三条均 Succeeded、ARCHIVED=true、6d21h 前执行
fcb-pipeline-12node-ggnvh12/126m
aurora-fcb-pipeline-r584f10/102m17s

这是「为 aurora 产品做容器化构建」的流水线,与 argo ns 的数据采集跑批(collecte-batch)并列为 Argo 在本集群的第二类生产业务。

🧩 关键机制:kubectl 查不到、UI 却能看 = 归档(archive)

sudo kubectl get wf fcb-pipeline-13node-d6pbp -n aurora-build -o yaml
# Error from server (NotFound): workflows.argoproj.io "fcb-pipeline-13node-d6pbp" not found
sudo kubectl get wf -n aurora-build
# No resources found in aurora-build namespace.

原理:controller 配置 persistence 归档后,工作流完成 → 过 TTL → CR 资源被 GC 删除,但完整定义、步骤图、日志已存进 Argo 自己的数据库。UI 列表 = 活资源 + 归档记录混合展示,归档条目照样能点开看 DAG / YAML / 日志。这也是 §07 待确认 #2 的部分答案:归档确认已开启,DB Pod 不在 argo ns(疑在 fke-db),configmap persistence 段待确认。

💡 解剖已归档流水线的三个途径:① UI 直接点开归档条目(零命令、图最全,右上角切 YAML 视图);② argo archive list / get(v3.4+ 子命令,走 argo-server API 读归档库);③ 等下次构建触发时 kubectl get wf -n aurora-build -w 抓活的。

09new-k8s 离线安装与维护(单点实战) ⭐

承接前面 01~08 章的线上摸底,本章是动手篇:在 new-k8s(离线)单点部署同款 Argo Workflows,版本对齐线上 v3.7.9(chart 0.45.28 + images.tag 钉死)。路线 = 9.1 安装定位 → 9.2 开发机下载清单 → 9.3 传输与导入 → 9.4 Helm 单点安装(values 全文 + 四个坑) → 9.5 验收三关(含离线 hello-world 与 mini-pipeline) → 9.6 维护手册 → 9.7 对外访问(NodePort + nginx 域名反代)。✅ 已实操上线(2026-11):两组件 Running,真实输出已回填。

9.1 安装定位:线上参照(fke)vs new-k8s 单点

new-k8s 这次安装对齐线上 fke 的版本(v3.7.9)和组件形态,但部署方式完全不同:

维度线上 fke(参照)new-k8s(本次目标)
版本v3.7.9(workflow-controller + argo-server)同 v3.7.9,与线上保持一致,便于经验迁移
安装方式Helm 在线装,release 名 fke,资源前缀 fke-argo-workflows-开发机下好 Chart 包 + 镜像 → ctr 导入 → Helm 本地 tgz 离线装,release 名 argo
拓扑controller / server 各 1 副本(实际就是单点形态)单点:默认即非 HA、无外部 DB、无 MinIO,chart 默认值就是单点,无需任何额外配置
命名空间argo(工作流也在 argo ns 跑)同样装到 argo ns,提交流程与线上一致
artifacts未验证(待查 controller configmap)首装不配置(chart 不依赖 MinIO/DB);后续要产物存储再加
网络内网 registry docker.fftaicorp.com/kube-public/完全离线:镜像以 ctr images import 落到节点本机
为什么"单点"反而省事:Argo Workflows 官方 chart 默认安装的就是非 HA 版(controller、server 各 1 副本,SQLite 级元数据、不接外部数据库)——线上 fke 的形态恰好就是它。所以 new-k8s 不需要写任何 HA / DB values,默认值即目标形态。

9.2 开发机下载清单(★ Chart + 镜像 + CLI)

9.4 Helm 单点安装(values 全文 + 两个必踩坑)

① values-offline.yaml(单点最小配置,全文)

# ===== Argo Workflows 离线单点安装 values(new-k8s)=====
# 单点 = chart 默认形态:非 HA、无外部 DB、无 MinIO,以下只写必须覆盖的四处
images:
  tag: v3.7.9               # ★坑1:不写则取 chart 内置 appVersion v3.7.4!必须钉死 v3.7.9 对齐线上
  pullPolicy: IfNotPresent  # ★坑2:chart 默认 Always,离线环境会去 quay.io 拉镜像 → ImagePullBackOff 卡死

# 资源名固定为 argo-*(不加则是 argo-argo-workflows-*,又臭又长)
fullnameOverride: argo

# ★坑3:UI 认证模式(chart 与官方清单的隐蔽差异)。官方 quickstart 显式带 --auth-mode=server,
# helm chart 默认不传 → argo-server 落到上游默认 client 模式 → 浏览器没 token,
# UI 调接口必报 code 16 "token not valid"。改 server 模式后浏览器免 token 直接用;
# 代价 = "能打开页面 = 全权操作",网关 nginx 必须加 basic auth!
server:
  authModes:
    - server
  # ★坑4:对外 NodePort 必须写进 values!kubectl patch 改的 NodePort 是带外改动,
  # helm upgrade 会按 chart 默认(ClusterIP、无 nodePort)把它冲掉 → 网关 nginx 直接 502(2026-11 实测)
  serviceType: NodePort
  serviceNodePort: 30274

# 以下全部走默认,即单点目标形态:
#   crds.install: true        → 首次 install 自动装 workflows.argoproj.io 全套 CRD
#   controller.replicas: 1 / server.replicas: 1 → 各 1 副本
#   不配 persistence/postgres → 不需要数据库
#   不配 artifactRepository   → 暂不启用 artifacts(后续要存储再加,可选 MinIO)

② 安装命令

进阶:仿线上 collecte-batch 的多步流水线(单点复刻版)

线上真实业务的运转方式:外部系统(Jenkins/GitLab/数据平台)提交带批次参数的 Workflow → controller 把每个 step 拆成独立 Pod 调度 → 步骤间靠 artifact 仓库传文件 / 参数传小数据 → 完成后归档 + TTL 清理(无 cronwf,不是定时驱动)。下面用参数传递串一条五步流水线(collect → convert → annotate×3 并行 → qc → downstream),复刻线上形态:

cat > mini-pipeline.yaml <<'EOF'
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: mini-collecte-
spec:
  entrypoint: pipeline
  arguments:
    parameters:
    - name: batch-id
      value: batch-001
  templates:
  - name: pipeline
    steps:
    - - name: collect
        template: collect
    - - name: convert
        template: convert
        arguments:
          parameters:
          - name: raw
            value: "{{steps.collect.outputs.parameters.raw-count}}"
    - - name: annotate
        template: annotate
        withSequence:
          count: "3"
        arguments:
          parameters:
          - name: valid
            value: "{{steps.convert.outputs.parameters.valid-count}}"
    - - name: qc
        template: qc
        arguments:
          parameters:
          - name: annotated
            value: "{{steps.convert.outputs.parameters.valid-count}}"
    - - name: downstream
        template: downstream
        arguments:
          parameters:
          - name: passed
            value: "{{steps.qc.outputs.parameters.pass-count}}"
  - name: collect
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [collect] batch={{workflow.parameters.batch-id}} fetched 100; echo 100 > /tmp/out"]
    outputs:
      parameters:
      - name: raw-count
        valueFrom:
          path: /tmp/out
  - name: convert
    inputs:
      parameters:
      - name: raw
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [convert] got {{inputs.parameters.raw}} raw, 95 valid; echo 95 > /tmp/out"]
    outputs:
      parameters:
      - name: valid-count
        valueFrom:
          path: /tmp/out
  - name: annotate
    inputs:
      parameters:
      - name: valid
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [annotate] worker on {{inputs.parameters.valid}} records, done"]
  - name: qc
    inputs:
      parameters:
      - name: annotated
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [qc] reviewed, 93 pass; echo 93 > /tmp/out"]
    outputs:
      parameters:
      - name: pass-count
        valueFrom:
          path: /tmp/out
  - name: downstream
    inputs:
      parameters:
      - name: passed
    container:
      image: busybox:1.36
      command: [sh, -c]
      args: ["echo [downstream] stored {{inputs.parameters.passed}} records, batch {{workflow.parameters.batch-id}} done"]
EOF
argo submit -n argo mini-pipeline.yaml --watch     # 预期 7 个节点全绿,annotate×3 并行
argo logs @latest -n argo | grep '^\['             # 看数据接力:100 → 95 → 93
与线上差距对照:① 线上步骤间传文件靠 artifact 仓库(S3/MinIO + persistence),单点要传真实文件需先架 MinIO 或用 volumeClaimTemplates 挂 PVC(workflow 级 emptyDir 每个 Pod 独立,不共享!);② 线上用 WorkflowTemplate 沉淀流水线定义、提交时只传参数(13node/12node 就是同模板不同参数),单点学习阶段内联即可;③ 坑(2026-11-19 首跑实测):executor 的 init 容器用的是 argoexec 镜像(chart 默认 quay.io/argoproj/argoexec:v3.7.9),与 argocli 是两个东西——离线清单漏了它,首个 Workflow 必卡 Init:ErrImagePull;修复见 9.6 小节报错表新增行。
验收进度(2026-11):关一 ✅ 两组件 1/1 Running(9.4 小节实测);关二、关三(CLI 连通 + 离线 hello-world)待执行——hello-world 的测试 Pod 会随机调度到任意节点,五台镜像都已导入,不用怕。

报错速查

现象原因处理
Workflow Pod 卡 Init:ErrImagePull执行器镜像 argoexec 不在节点上——离线导入清单只有 controller + argocli,而 chart executor 默认 quay.io/argoproj/argoexec:v3.7.9,首个 Workflow 跑到一半才暴露(2026-11-19 mini-pipeline 首跑实测)确认 init 要的名字:kubectl get pod <pod> -n argo -o jsonpath='{range .spec.initContainers[*]}{.image}{\"\\n\"}{end}' → 开发机下载 argoexec(出不了 quay 可用 docker.1ms.run 中转后 docker tag 改回原名)→ 五台节点 sudo ctr -n k8s.io images import → 删掉卡住的 wf 重提
Pod ImagePullBackOffpullPolicy 还是默认 Always,在连 quay.iovalues 改 IfNotPresent 后 helm upgrade;并 ctr -n k8s.io images list 确认镜像真的导进去了
装出来版本是 v3.7.4没写 images.tag,回落 chart 内置 appVersionimages.tag: v3.7.9 钉死后 upgrade
UI 报 {"code":16,"message":"token not valid"}chart 默认不传 --auth-mode,上游默认 client 模式,浏览器没 token(官方清单默认 server 模式所以没这问题)values 加 server.authModes: [server] 后 helm upgrade,浏览器强刷;server 模式=免登录全权限,网关 nginx 务必开 basic auth
helm upgrade 后旧 Pod 显示 Terminating → Error滚动更新正常收尾:新 Pod Ready 后旧 Pod 收 SIGTERM 退出,非零码退出被标 Error,随即对象删除不是故障;确认新 ReplicaSet 的 Pod 1/1 Running 即可,几秒后旧 Pod 自动消失
upgrade 后网关 502 Bad Gateway,域名打不开helm upgrade 按 chart 默认把 kubectl patch 的 NodePort 冲回 ClusterIP,30274 没了kubectl -n argo get svc argo-server 确认;values 声明 serviceType/serviceNodePort 后再 upgrade(详见 9.7 小节告警框)
提交的 Workflow 一直 Pending节点资源不足 / selector 不匹配describe pod 看事件;单点节点注意预留资源
Workflow 卡 Running 不结束经典坑:容器主进程退了但 wait 边车(或被注入的 sidecar)不退出确认 workflow 是否被注入额外 sidecar,必要时加 sidecar.istio.io/inject: "false" 类注解后验证
UI 打不开(localhost:8080)连错端口::8080 是 controller 的 metrics,不是 APIUI/API 走 argo-server:2746,见 本页 §03 端口陷阱

9.7 对外访问:NodePort + nginx 域名反代(80→301→443)

照 new-k8s Longhorn 的老套路:svc patch 成命名 NodePort → 网关 nginx(new-k8s-nginx-1)80 转 301、443 反代五节点。目标域名:new-argoworkflows.fftaicorp.com(网关实机证书为 _.fftaicorp.com 泛域名,域名匹配直接绿锁)

① argo-server svc 开 NodePort(命名端口 30274)

kubectl patch svc argo-server -n argo \
  -p '{"spec":{"type":"NodePort","ports":[{"name":"web","port":2746,"targetPort":2746,"nodePort":30274,"protocol":"TCP"}]}}'

kubectl get svc argo-server -n argo    # 2746:30274/TCP 即成功
curl -I http://10.18.51.121:30274/     # 任一节点返回 HTTP 200/302 即通
⚠️ 实测坑(2026-11):NodePort 千万别只靠 kubectl patch!patch 是带外改动,下一次 helm upgrade 会按 chart 默认把它冲回 ClusterIP(30274 消失),网关立刻 502、域名打不开。正确姿势:values 里声明 server.serviceType: NodePort + server.serviceNodePort: 30274,让 helm 自己管。排查口诀:502 先看 kubectl -n argo get svc argo-server 里 30274 还在不在。
✅ 实测(2026-11):patch 一次成功,2746:30274/TCP;首次 curl 偶发 connection refused,1 秒后重试即 200——patch 后 kube-proxy 的 iptables 规则同步有秒级延迟,不是故障。HTTP 200 直出也顺带证实了 --secure=false(argo-server 内部就是纯 HTTP,nginx 可放心写 proxy_pass http://)。

② 先验内部 TLS 模式(决定 nginx upstream 用 http 还是 https)

kubectl get deploy argo-server -n argo -o yaml | grep -- '--secure'
# chart 默认 --secure=false → argo-server 内部走纯 HTTP,nginx 直接 proxy_pass http://
# 若是 --secure=true(自签 HTTPS)→ upstream 改 https:// 并加 proxy_ssl_verify off;

③ 网关 nginx 配置(/etc/nginx/conf.d/new-argoworkflows.fftaicorp.com.conf,已实测部署)

upstream argoworkflows_ui {
    server 10.18.51.121:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.122:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.123:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.124:30274 max_fails=2 fail_timeout=10s;
    server 10.18.51.125:30274 max_fails=2 fail_timeout=10s;
}
server {
    listen 80;
    server_name new-argoworkflows.fftaicorp.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl http2;    # 语法坑:nginx < 1.25.1 不认独立的 "http2 on;" 指令(new-k8s-nginx-1 实测报 unknown directive)
    server_name new-argoworkflows.fftaicorp.com;

    ssl_certificate     /etc/nginx/ssl/_.fftaicorp.com.pem;    # 网关实机泛域名证书,域名匹配直接绿锁
    ssl_certificate_key /etc/nginx/ssl/_.fftaicorp.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;

    # 建议开启:argo-server 默认 auth-mode=server,UI 本身不登录,
    # 外层 basic auth 就是唯一门锁(照 Longhorn 惯例)
    #auth_basic "argo workflows";
    #auth_basic_user_file /etc/nginx/htpasswd/argoworkflows;

    location / {
        proxy_pass http://argoworkflows_ui;
        proxy_set_header Host            $host;
        proxy_set_header X-Real-IP       $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_http_version 1.1;                      # 日志流 / WebSocket 必须带
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
        client_max_body_size 0;
    }
}
nginx -t && nginx -s reload
upstream 为什么写全部 5 台(含 121/122 两台 master)而不是只写 worker?NodePort 是 kube-proxy 层的东西:每台节点的 30274 都在监听,流量从任一节点进来,kube-proxy 都会转给 Service 背后的 Pod——实测就是证据:Pod 只在 n3,从 m1(121)的 30274 进,照样 200。master 的污点(NoSchedule)只挡"调度 Pod",不挡"转发流量"。两种写法都合法:写 5 台 = 入口池最大、任一节点维护时入口不断、与 Longhorn 站点配置同构好排查;只写 123/124/125 三台 worker 也完全能跑(master 不承载业务入口、省 master 的 conntrack/带宽、防火墙少开两个口),按团队规范选即可,小集群实际差异微乎其微。

④ DNS 与安全

  • 内网 DNS 加 A 记录:new-argoworkflows.fftaicorp.com → nginx 网关 IP(与 Longhorn 同套路);
  • 浏览器验收:https://new-argoworkflows.fftaicorp.com → Argo Workflows UI,绿锁(网关证书 _.fftaicorp.com 泛域名匹配);
  • 安全红线:30274 只对网关 IP 放行(防火墙堵旁路),别全网段裸奔——fke 上 30010 裸奔 447 天的教训就在档案里。
为什么走 NodePort 直连而不是 ingress-nginx:ingress-nginx(30080/30443)建 Ingress 转发当然也行,但 NodePort 直连与 Longhorn 运维套路一致、链路少一层、排查简单;Argo UI 的 WebSocket 日志流在两层代理里都得带 Upgrade 头,链路越短越不容易踩坑。
